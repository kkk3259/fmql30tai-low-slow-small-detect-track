# 模型侧交付清单（yolo11n_drone · 截断版 INT8）

日期：2026-10-20。模型：YOLOv11n（单类 drone），DUT Anti-UAV 训练（best.pt 第 98/100 轮），
Icraft v3.39.0 INT8 量化（per-channel，kld，128 张 DUT 校准图已入库 `deploy/calib/`）。

## 1. 输入规格

| 项 | 值 |
| --- | --- |
| 尺寸 | 640×640（`net_w: 640, net_h: 640`） |
| Layout / dtype | **NHWC，UINT8**（`[1, 640, 640, 3]`，RGB 顺序） |
| 归一化 | **已折入量化**（pre_scale=255, pre_method=nop）——板端送原始 0~255 像素即可，**不要再除 255** |
| 预处理 | letterbox 或直接拉伸均可（训练用 letterbox；拉伸已验证可用，见《模型与部署说明.md》） |

## 2. 输出规格（截断头，无 DFL/Sigmoid/NMS）

| 张量 | 形状 | dtype/layout |
| --- | --- | --- |
| box_raw | `[1, 64, 8400]` | **fp32，通道优先（[1,C,N]）** |
| cls_raw | `[1, 1, 8400]` | fp32，通道优先 |

ZG.json 中 op275（输出节点）为 Host 侧，输出已**反量化为 fp32**，后处理直接读浮点。
**8400 排列**：8 倍层 80×80 → 16 倍层 40×40 → 32 倍层 20×20，层内**行优先**（y 外层、x 内层）。

## 3. CPU 后处理（参考实现 `deploy/cpu_decode_demo.py`，已数值验证）

1. box_raw reshape `[1,4,16,8400]` → softmax(16) × [0..15] 求和 = **DFL 解码** → ltrb 距离 `[1,4,8400]`
2. anchor 中心：grid 单位 `(x+0.5, y+0.5)`，每层乘对应 stride
3. `cx = ax − lt·s`、`cy = ay − lt·s`、`w = (lt+rb)·s`、`h = (lt+rb)·s`（ltrb 为 grid 单位距离）
4. `conf = sigmoid(cls_raw)`
5. 阈值 **conf ≥ 0.25**（DUT test 评估用值），NMS **IoU ≥ 0.45**
6. 单类无类间 NMS 问题；max_det 建议 300

## 4. view_except_op_ids：`[0, 275]`

来源：解析 `yolo11n_drone_trunc_ZG.json` 的 `ops[].compile_target` ——254 个 op 中
252 个 `@zhuget(330)`，仅 2 个 `@hostt`：**op0 = 输入节点、op275 = 输出节点**。
比官方 v5 示例（5 个）更干净：截断头后全网都跑 NPU。

## 5. 量化信息

- 方式：INT8 per-channel，饱和策略 kld，校准集 `deploy/calib/dut/`（128 张，`dut.txt` 列表）
- 输入量化：UINT8 进图，scale（=1/255 及首层校准）已由量化网络吸收
- 输出：fp32（工具自动反量化），无需板端乘 scale
- INT8 vs FP32 对拍（宿主机，12 张 DUT）：框 IoU 均值 0.907，conf 平均差 0.108（含 letterbox/拉伸预处理差异）
- 各层逐 op 量化 scale 可在板上用 pyrtutils 的 `NetInfo.py` 从 ZG.json 读取（`ops[].inputs/outputs[].dtype`）

## 7. 关于 352×640（官方示例输入尺寸）的结论

**主交付保持 640×640，另补 352×640 变体（如目录存在 `*_plin_352x640_*`）。**

判断依据：
- 对 16:9 视频源（1920×1080/1280×720），640 宽 letterbox 到 352 高几乎无 padding——
  **远处目标的采样分辨率与 640×640 完全相同**（宽度决定的横向分辨率不变），计算量省 ~25%；
- 我们的 test 指标（mAP50 0.920）本就是 ultralytics 按 rect 推理评估的（16:9 图实际推理尺寸
  即 640×384 一档），352×640 部署与之同级；
- 4:3 图片（DUT 少量）在 352 高度下缩得略小，影响可忽略（自采数据将以 16:9 为主）。

结论：**352×640 够用且更省**，与官方 PLin 通路规格一致；640×640 保留为已完整验证的主版本。
两者模型文件独立，yaml 仅 `net_w/net_h` 与文件名不同（352 版的 view_except_op_ids 以其
ZG.json 解析结果为准，随文件附带）。
