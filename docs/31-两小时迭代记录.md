## 二、两条"想提升灵敏度"的路，走不通的已证伪

### 2.1 PS 侧局部均值高通（❌ 反而更差）

思路：先在 PS 里做 `img - blur31(img)`，把云的慢变纹理拉平，小目标就好检。

实测（`--pre hp`，同上 8 段）：

```
平均召回 2.3%   平均精确 1.3%   候选 5.2/帧
```
比不处理（13.5%）**更差**。

原因：31×31 均值窗里也包含目标自身的能量，减掉后目标反差被削弱；而 Top-Hat 之后本来就没剩多少。

### 2.1b **gamma 曲线预处理（✅ 找到了，效果最大）**

思路：送 PL 之前先做幂律拉伸 `out = 255·(x/255)^γ`（γ<1 提亮暗部）。

机制：γ 把**背景的动态范围压扁**（云的明暗差被压到很小），CFAR 的 `mean + K·sd + floor` 里 `sd` 项随之变小，弱目标的局部反差相对就突出了。这不是"调亮度"，是改变了 CFAR 自适应门限的统计特性。

实测（同一 12 段测试集，`--inv both --border 24`）：

| γ | 平均召回 | 平均精确 | 候选/帧 |
|---|---|---|---|
| 1.0（原样） | 9.0% | 0.9% | 22.2 |
| 0.70 | 14.9% | 2.1% | 27.9 |
| 0.50 | 31.5% | 3.2% | 32.3 |
| 0.35 | 45.4% | 7.7% | 21.5 |
| 0.20 | 55.4% | 38.7% | 16.4 |
| 0.12 | 69.0% | 43.2% | 15.2 |
| 0.08 | **76.6%** | 54.9% | 10.6 |
| 0.05 | 66.2% | **73.2%** | 6.6 |

- γ=0.08 召回最高（76.6%），γ=0.05 精确最高（73.2%）且 F1 更好（0.70 vs 0.64）
- **F1 最优区间 γ≈0.05~0.08**，召回相比原样提升 **8.5 倍**，精确提升 **81 倍**

γ=0.05 的分场景表现：

| 场景 | 召回 | 精确 |
|---|---|---|
| grass_man | 97.5% | 72.4% |
| sky_bird_multi | 92.7% | 99.8% |
| sky_tiny | 92.6% | 100.0% |
| sea_plane | 92.3% | 98.4% |
| grass_car | 91.2% | 92.0% |
| sea_bird | 90.8% | 99.8% |
| sky_plane_far | 68.1% | 50.7% |
| clouds_drone | 61.0% | 67.5% |
| clouds_bird | 53.8% | 94.2% |
| sky_drone_multi | 23.8% | 96.6% |
| night_drone | 19.0% | 4.3% |
| night_bird | 12.0% | 3.0% |

**弱点仍在夜间**（强噪点把 CFAR 的 σ 抬高，目标被淹）——这是下一轮要攻的点。

代码：`--pre gamma --gamma 0.05`（评估脚本）/`--gamma 0.05`（`cam_pipe.py`、送 PL 前拉伸，显示画面不受影响）。

## 七、三域时序违例的根因（已查清）

`ours3d_timing.rpt` 里最差路径：

```
Slack (VIOLATED) : -0.702ns
Source: U0_ps_ai_wrap_demo/.../u_ddr_phy_wrcal/po_stg2_wrcal_cnt_reg[0]/C
Destination: U0_ps_ai_wrap_demo/.../u_ddr_phy_wrcal/gen_mux_rd_div4.../D
Path Group: clk_pll_i (200 MHz)
Data Path Delay: 5.626ns  (logic 0.449ns 8%  route 5.177ns 92%)
```

- 全部落在 **MIG DDR3 的写校准（wrcal）逻辑**里，**没有一条在我们的检测器或 LA 上**。
- 92% 是布线延迟 ⇒ 是 **90.88% 占用导致布线绕远**，不是逻辑本身慢。
- 学长那版同结构设计 WNS −0.065（占用低，挤得开）。
- 缓解方向：降低占用（MAX_CAND 16→8、去掉 LA）让 MIG 拿到好位置；或给 MIG 加 `-directive Explore` 布线。

> 影响面：若这条路径真的失效，DDR3 写校准可能失败 → 我们的检测器读不到帧。上板后先用 `detect3d.py` 确认 PL DDR 读写正常。

## 八、离线仿真证明：适配层与检测器功能正确（15:00）

板子 14:30 起 ping 不通（需断电），改走离线仿真。用 `pl/tb/tb_user_op_la128.v`（128×64，
平台时钟 200 MHz，核 50 MHz），除了层次化读 LA 内存，还加了内部进度探针直接看
`dut.u_ip2` 的 `pcount / ocount / fst / thv_cnt / cfv_cnt`：

```
T=100M  pcount=0     ocount=0    fst=2  (F_FEED 前，等 start)
T=200M  pcount=0     ocount=0    fst=2
T=300M  pcount=996   ocount=0    fst=3  thv=520   cfrdy=996
T=400M  pcount=5471  ocount=0    fst=3  thv=5520  cfv=3010
T=500M  pcount=8192  ocount=0    fst=3  thv=10520 cfv=7485  cfrdy=8713
T=600M  pcount=0     ocount=116  fst=5  (F_WAIT，等写回 DDR)
```

**解读**：
- 整帧 8,192 像素全部喂完（`pcount` 到 8192 后清零）。
- CFAR 输出 7,485 个有效像素（`cfv`），与 8192 减边界一致。
- **CCL 产出 116 字节候选表**（MAX_CAND=16 时 `1+16×7=113`，按 4 字节对齐到 116）。
- 状态机走到 `F_WAIT`，说明“检测→取候选”整条路在仿真里是通的。

**之前 `STATUS=busy / done=0` 是假象**：测试台只建模了 AXI **读**通道，没建模写通道
（`wr_busy/wr_done` 永远不响应），所以状态机停在“等写完成”。不是设计错误。

**推论**：板上 `err=1` 不可能是功能逻辑错，最可能是**时序违例**（第七节的 WNS −0.703）。
MIG 的 wrcal 路径跑不过 → PL DDR 数据读写不可靠 → 检测器读到错数据 → 超时报 err。

## 九、仿真脚本的坑（留给以后）

1. **`reg itf_arready = 0;` 会让平台永不就绪** —— 首跑看到 `DBG_AR=0 / DBG_WD=20`，
   误判成“AR 从不握手”，其实是测试台自己把 ready 拉低。初值必须 `= 1`。
2. **tb 里 `disable la_dump;` 语法非法**（没有命名块），改成 `if (i <= k)` 守卫。
3. **层次化探针比走寄存器读 LA 快得多**：`dut.la_mem[(k-i)&63]` 直接读，
   不用每读一条都跑一次 AXI 寄存器事务。
4. **小图必须满足窗口约束**：64×48 时 CFAR 的 31×31 窗比图还大，测不出候选；
   128×64 与 320×180 都可用。
