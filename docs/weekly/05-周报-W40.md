### 1.2 平台硬约束（决定了技术路线）

- lite 版**未焊接** PL 侧千兆网、SDI 输入输出、SFP 光口、PL 端 eMMC、CAN、RTC、EEPROM 等；
- → **数据/视频输入必须走 PS 侧**（USB 摄像头 V4L2 / 序列回放），不得依赖 SDI 与 PL 高速接口；
- → 无 RTC（断电丢时间）；HDMI 固定 720P60；USB2.0 带宽有限（720P YUYV 超限 → 相机须用 MJPG）。

### 1.3 技术路线规划（三层异构）

```
PS（采集/调度/输出） → PL（像素级运算） → NPU（ROI 判别） → PS（跟踪/显示/上报）
```

规划要点：
1. **先软后硬**：先在 PC 上用 Python/OpenCV 建立完整算法基线，再逐模块迁移到 PL；
2. **以软验硬**：每个 PL 模块用 OpenCV 生成"标准答案"，仿真阶段逐像素比对；
3. **数据驱动**：关键参数用消融实验确定，而非经验假设。

### 5.2 实验结论（能力边界）

**单帧检出能力边界**（[实验] `results/sweep_synth.csv`，9 组，每组 **120 帧**）：

| 目标对比度 | 半径 1.0 px | 半径 1.5 px | 半径 3.0 px |
|---|---|---|---|
| 5 灰阶 | 0% | 0% | 0.8% |
| 15 灰阶 | 35.0% | 93.6% | 100% |
| 30 灰阶 | 85.0% | 100% | 100% |

**高斯去噪消融**（[实验] `results/ablation_gauss.csv`，12 组，每组 **150 帧**；对比度固定 15 灰阶）：
> **说明**：本表与上表的同类数据点略有差异（例如「半径 1.0 / 对比度 15」——上表 31.7%、本表 35.0%），原因是两组实验的合成序列**帧数不同**（120 帧 vs 150 帧），统计样本量不同所致，**并非数据矛盾**。

| 目标半径 | 高斯关 | 高斯开 | 差值 |
|---|---|---|---|
| 1.0 px | 35.0% | 0.0% | −35.0% |
| 1.5 px | 93.6% | 47.9% | **−45.7%** |
| 3.0 px | 100% | 100% | ±0.0% |

**理论验证**：3×3 高斯核中心权重 0.25（点目标峰值降至 1/4），噪声衰减 0.375 倍 → **SNR 下降 33.3%**（本人独立验算，数值与队友推导一致）。

**时域增强实验**（[实验] `results/v3_temporal_sweep.csv`）：

| 对比度 | 单帧基准 | bg 背景差分 | acc 多帧平均16 | tmax 时间TopHat8 | mc 运动补偿16 |
|---|---|---|---|---|---|
| 9 | **12.1%** | 10.0% | 0.0% | 0.0% | 0.0% |
| 11 | **48.6%** | 36.4% | 0.0% | 8.6% | 0.0% |
| 13 | **82.1%** | 73.6% | 0.0% | 28.6% | 0.0% |

**结论**：像素域时域方法**均未超过单帧基线** → 有效手段是**航迹级时域确认**（v2 已实现）。

## 九、补充：真实数据验证（W40 尾段新增，进行中）

### 9.1 为什么做

此前所有结果都来自**合成序列**（人工云团背景），存在"自证"问题：评委可能质疑"真实场景能不能用"。
因此引入**公开视频**做真实场景验证。

### 9.2 方法与新增工具

| 步骤 | 工具 | 说明 |
|---|---|---|
| ① 获取素材 | Pexels 免费视频（1080P/4K，可商用） | 下载 4 段：天空+云+飞鸟/客机、纯云层 |
| ② 规格化 | **新增** `tools/make_lowslow_seq.py` | 裁剪 + 缩放到标准输入（1280×720），含抽帧预览与缩放方向检查 |
| ③ 数据集接入 | **新增** `tools/dataset2seq.py` | 公开数据集（Anti-UAV / UAV123 / 图片序列）→ mp4 + `frame,x,y` 真值 |
| ④ 标注真值 | `tools/mark_gt.py` | 关键帧 + 线性插值：本次标 **12 个点 → 插值出 630 帧逐帧真值** |
| ⑤ 评测 | `baseline/detect_v1.py`、`track_v2.py`、`ps/ps_app.py` | 统计 Pd / 虚警 / 跟踪成功率 |

### 9.3 素材分析（自动检测，非目视）

对 4 段视频抽帧分析（调我们的检测链）：

| 素材 | 分辨率 | 目标 | 目标尺寸 | 图像 σ（杂波强度） |
|---|---|---|---|---|
| num2 | 1920×1080 | **飞鸟** | **约 30×15 px** | **10.9** |
| nom1 | 1920×1080 | 客机 | 约 100×60 px | 46.0 |
| num4 | 3840×2160 | 无目标（纯云层） | — | 42.0 |
| 合成序列（对照） | 1280×720 | 合成点目标 | 1.5 px（半径） | 9.2 |

**首次发现**：真实图像的杂波强度 σ（10.9~67.4）**高于合成序列（9.2）**，且每张抽帧都**填满 8 个候选槽**（`topk` 上限）→ 说明真实场景虚警压力显著更大。

### 9.4 完整评测结果（飞鸟序列，630 帧 = 21 秒）

| 指标 | 数值 | 对照（合成序列） |
|---|---|---|
| 处理帧数 | **630** | 150 |
| **检出率 Pd** | **40.8%**（命中 257 / 漏检 373） | **94.7%** |
| **虚警率** | **12797 次/分钟** | 384 次/分钟 |
| 平均候选/帧 | **7.52**（上限 8） | 1.16 |
| **跟踪成功率** | **97.0%**（611/630） | 98.7% |
| **ID 切换** | **19 次** | 0 |
| 单帧耗时 | 3.99 ms | 4.19 ms |
| 端到端帧率 | 95.18 fps | 93.43 fps |

**★ 本组数据的关键发现**：

```
检测层：Pd      94.7%  →  40.8%    （暴跌 54 个点 ✗）
跟踪层：成功率  98.7%  →  97.0%    （仅降 1.7 个点 ✓）
```

**检测层"崩了一半"，跟踪层却几乎不受影响** —— 说明「航迹级确认」有效弥补了检测层的缺陷：
系统最终仍只输出 **1.00 条航迹/帧**，跟踪成功率保持 **97.0%**。代价是 ID 切换由 0 升至 19 次。

### 9.4b 机理定位（逐环测量，非推测）

为找准原因，我们在真值坐标处**逐环测量**（工具：`tools/diag_signal.py`）：

| 环节 | 均值 | 说明 |
|---|---|---|
| 目标处灰度值 | 183.9 | 目标本身很亮 |
| 目标处 Top-Hat 增强值 | **34.87** | 有增强 |
| CFAR 门限 | **25.07** | 其中 k×局部标准差 ≈ 22、floor 仅 3 |
| 目标/门限 比值 | **1.39** | 处于同一量级 |
| 目标处过门限率 | **53.5%** | 只有一半 |

**结论：目标增强值与局部噪声门限同量级（信噪比约 1.6）→ 单帧检测已达能力极限** ✗
提高门限压虚警会同时滤掉目标；降低门限提检出则虚警爆炸。

### 9.4c 被排除的两条推测路径（重要）

| 尝试 | 结果 | 结论 |
|---|---|---|
| `--topk 16`（扩大候选数） | Pd 40.8% → **41.0%** | ❌ **排除**"真目标被挤出候选前列"的解释 |
| `--tophat 15`（改大结构元） | Pd 40.8% → **29.2%** | ❌ **排除**"结构元尺寸失配"的解释 |

> **方法论收获**：最初两条解释都是**凭推测**得出的，被实验否定 ✗。
> 改用**逐环测量**才定位到真实机理（信噪比不足）。
> **教训：先测量，再下结论。**

### 9.5 关键发现（机理）

```
真实图像杂波强（σ=10.9 > 合成 9.2）
        ↓
CFAR 门限（k=4 / floor=3，在【合成序列】上调定）不适配真实场景
        ↓
虚警暴涨 → 每帧填满 8 个候选槽（topk 上限）
        ↓
★ 真目标被虚警挤出候选前列 → Pd 由 94.7% 跌至 36.7%
```

**三点结论**：
1. **量化了"合成→真实"的性能落差**（Pd 94.7% → 36.7%），并给出了**具体机理**（候选槽被虚警占满）；
2. **印证了技术路线的正确性**：跟踪成功率仍有 **93.3%** → 说明**航迹级确认有效**，这正是我们设计 NPU 精判 + 3 帧确认的原因；
3. **暴露了工程问题**：检测门限与候选数量（`topk`）**必须在真实数据上重新标定**，不能直接沿用合成序列的调优值。

### 9.6 顺带发现并修复的 3 个缺陷（只在真实数据下暴露）

| # | 缺陷 | 触发条件 | 状态 |

> **意义**：这 3 个缺陷**只对真实视频暴露**（此前一直跑 `--src synth` 所以没发现）——
> 这本身证明了"用真实数据验证"的必要性，也体现了工程严谨性。

### 9.4d 时域增强的实测收益（★ 正面结果）

针对"单帧信噪比不足"，我们验证了时域增强接入**跟踪链路**的效果（真实视频 630 帧）：

| 配置 | 原始候选/帧 | 虚警(次/分) | **跟踪成功率** | **ID 切换** |
|---|---|---|---|---|
| 基准（无时域） | 7.52 | 22360 | 97.0% | 19 |
| **★ 运动补偿 mc n=16** | **1.87** | **1137** | **97.1%** | **15** |
| 对照：多帧平均 acc n=8 | 1.82 | 1271 | 94.8% | 13 |

**结论：运动补偿时域增强是"纯赚"的优化** ✓
- 虚警 **降 95%**（22360 → 1137）
- 跟踪成功率 **不降反升**（97.0% → 97.1%）
- ID 切换 **改善**（19 → 15）
- 候选数 **降 75%**（7.52 → 1.87/帧）→ **NPU 推理负载减轻约 4 倍** ✓
- 代价：单帧耗时 +0.8 ms（6.51 → 7.35 ms）

**⚠️ 重要修正**：此前根据合成序列的实验，我们曾判断"时域积累无效" ✗。
但在真实视频上（目标 10×5 px，比合成的亚像素目标大得多），
**带运动补偿的时域积累显著有效** ✓。
**说明同一技术在不同目标尺度下收益差异本质不同** —— 这也是"用真实数据验证"的价值。

**代码变更**：`baseline/track_v2.py` 新增 `--temporal {none,acc,mc,bg,tmax,both}` 等参数（复用 `detect_v3.TemporalEnhancer`）。


### 9.4e 时域增强接入完整链路（端到端对比）

把运动补偿时域增强接入 `ps_app.py`（7 环节集成程序）后实测（630 帧）：

| 指标 | 基准（无时域） | **mc n=16** | 变化 |
|---|---|---|---|
| 端到端帧率 | 90.29 fps | **72.10 fps** | −18 fps |
| 单帧总耗时 | 8.91 ms | 11.72 ms | +2.81 ms |
| ② 检测 | 4.43 ms | 7.49 ms | +3.06 ms（时域开销） |
| **检测候选总数** | 4736（7.52/帧） | **1178（1.87/帧）** | **−75%** ✓ |
| **跟踪成功率** | 97.0% | **97.1%** | 持平略升 ✓ |
| 告警条数 | 628 | 628 | 持平 |

**关键洞察**：软件端时域增强的 +3 ms 开销主要来自"每帧 16 次亚像素插值对齐" ✗；
**若在 PL 上实现**（帧缓存 BRAM + 移位读出对齐，无插值/浮点），**额外延迟将显著更低** ✓。
→ **时域增强是"适合交给 PL"的典型任务**，与"像素级运算卸载到 PL"的总体思路一致 ✓

**代码变更**：`ps/ps_app.py` 的 `Detector` 新增 `temporal / n-acc / alpha / vel-x / vel-y` 参数并在主程序传入。
