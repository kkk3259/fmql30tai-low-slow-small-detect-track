## 1. 帧缓冲区（板载 U-DMA-BUF，实测确认）

| 项 | 值 |
|---|---|
| 设备节点 | `/dev/udmabuf0`（char 242:0） |
| 物理基址 | **`0x30100000`** |
| 总容量 | 128 MiB（134,217,728 B） |
| 驱动 | ikwzm u-dma-buf 3.2.5 |
| sysfs | `/sys/class/u-dma-buf/udmabuf0/` |
| `sync_mode` | 1（可按 offset/size 局部同步） |
| `dma_coherent` | **0（非缓存一致，必须手动 sync）** |
| 一帧大小 | **230,400 B**（640×360 灰度，8 bit/像素） |
| 第 k 帧地址 | `0x30100000 + k × 230400` |
| 内存归属 | `/proc/iomem` 的 `2fded000-3fffffff` reserved 区（官方给 PL/DMA 留的 258 MB） |

### 1.1 128 MiB 分区

| 区间 | 大小 | 用途 |
|---|---|---|
| `0x30100000` ~ `0x30FFFFFF` | 16 MiB | **输入帧区**（PS 写 / PL 读），72 帧 |
| `0x31000000` ~ `0x310FFFFF` | 1 MiB | **输出区**（PL 写 / PS 读） |
| `0x31100000` ~ `0x380FFFFF` | 111 MiB | 备用（多缓冲 / 中间结果） |

## 2. 输出区布局（PL 写）

| 偏移 | 长度 | 内容 |
|---|---|---|
| `0x31000000` + 0 | 36 B | **候选表**（见 §2.1） |
| `0x31000040` + 0 | 4 B | **状态字**（见 §2.2） |
| `0x31000044` + 0 | 4 B | **邮箱请求字**（PS 写 / PL 读，见 §3） |

候选表与状态字放在同一 sync 区间（`sync_offset=0`、`sync_size=44`），PS 一次 sync 全看到。

### 2.1 候选表格式（36 B，PL → PS）

```
byte 0        : n_cand     候选个数（0 ~ 5）
byte 1  ~ 7   : 候选 0      x_hi, x_lo, y_hi, y_lo, 0, area, peak
byte 8  ~ 14  : 候选 1      （同上，7 字节/候选）
byte 15 ~ 21  : 候选 2
byte 22 ~ 28  : 候选 3
byte 29 ~ 35  : 候选 4
```

- `x`、`y`：16 bit 大端（`x_hi` 在前），**连通域质心坐标**，单位为 640×360 降采样后的像素
  - 语义依据：`baseline/detect_v1.py:extract_candidates` 直接取 `cv2.connectedComponentsWithStats` 的质心输出 `cents[i]`；PL 侧 `candidate_extract.v` 同为 8 连通 CCL 质心计算；`roi_pack.v` 亦以 `(cx, cy)` 为中心裁块 —— 三方一致
  - ⚠️ 历史勘误：本文档 v0.1~v0.3 曾在此处写「左上角坐标」，错误。§7 第 5 条已澄清为质心
- `byte 4`：预留恒 0（原 area 高字节位置）
- `area`：8 bit 连通域面积（像素数），范围过滤 `[2, 200]`
- `peak`：8 bit 连通域内增强图最大值
- 候选按 `peak` **降序**排列，最多 5 个；不足则 `n_cand` 之后填 0

#### 2.1.1 质心精度验收指标（2026-10-26 新增）

**下游级联判别的 ROI 裁剪以该质心为中心，因此质心误差直接决定判别命中率。经验证实验标定：**

| 质心偏移 | ROI 判别命中率 | 说明 |
|---|---|---|
| ±0 px（真值中心）| 91%~95% | 上限参考 |
| **±16 px** | **无影响** | 与真值中心持平 |
| **±32 px** | **≥85%** | 仍可用 |

- 偏移量单位为**原图 1280×720 的像素**；±32 px 相当于原图宽度的 5%
- 结论：**PL 粗筛输出的质心误差应控制在 ≤32 px（5%）以内**；±16 px 以内无精度损失
- 机理：448×448 的 ROI 视野是典型目标（15~35 px）的 13~30 倍，天然容纳粗筛误差
- ⚠️ 若粗筛误差超过 32 px，必须重新评估 ROI 裁剪边长（加大边长以容纳误差），不可直接沿用 448

#### 2.1.2 ROI 裁剪边长（2026-10-26 定版）

| 项 | 约定 |
|---|---|
| **裁剪方式** | 以质心为中心，**固定边长 448 px**（越界时推回贴边保边长不变：`x0 = max(0, min(cx - s/2, W - s))`）|
| **判定依据** | 板端 100 目标（test 集独立抽样，四尺寸档各 25）：448 → 95.0%，512 → 94.0%，差异在抽样波动内；448 单次前向快 3.2 ms，故取 448 |
| **⚠️ 待改** | `pl/rtl/roi_pack.v` 当前实现为「以 (cx,cy) 为中心裁 **128×128**」，与本约定不符，**需更新为 448×448**（P 负责）|

### 2.2 状态字（4 B，PL → PS）

| bit | 含义 |
|---|---|
| 31 | `done`：本帧处理完成（PL 置 1） |
| 30 | `error`：AXI 读超时/异常（PL 置 1） |
| 29:16 | 保留（0） |
| 15:0 | `frame_id`：本次处理的帧号（与邮箱请求字一致，取低 16 位） |

PL 在开始处理新帧时把 `done` 清 0，处理完置 1 → PS 用 `done` 上升沿判断可取结果。

### 2.3 地址归属与冲突（重要）

| 地址段 | 归属 | 本设计能否用 |
|---|---|---|
| `0x40000000 ~ 0x400000E3` | **AI_Mate（NPU）寄存器窗口**，实测 224 B | ❌ **绝对不能用** |
| `0x80000000` | **AI_Mate 的 DMA 窗口**（`--backends "...&dma=0x80000000"`） | ❌ 合一位流时不能用 |
| `0x30100000`（udmabuf 128 MiB） | 输入帧 + 输出区 | ✅ 本设计的 AXI 主口读写目标 |
| **`0x83C00000`（建议 256 KB）** | **本设计 AXI4-Lite 从口**（控制/状态寄存器） | ✅ 建议分配，和上面两段都不重叠 |

⚠️ **PL 与 NPU 不能共存**（同一时刻只有一份位流在跑）：
- 本设计的位流替换官方位流后，NPU（AI_Mate）就不存在了，`0x40000000` 也不再响应；
- 反过来，官方位流里也没有我们的 IP2；
- 要共存只有一条路：在 Procise 里把 `AI_Mate.edif`（及它需要的 DDR3 MIG / AXI 互联）当黑盒例化进我们的顶层 —— 属于"从零重建"，暂不做；
- 答辩层面两套位流可以分别演示、分别录屏，报告里说明"两种工作模式"即可。

⚠️ `0x40000000` 和 `0x80000000` 在 `/proc/iomem` 里都**不是**已注册外设（是位流里的 AXI 从设备/窗口），所以"读全 F"或"读 0xAA"都不能证明它没被用——以功能实测为准。

## 3. 触发与寄存器接口（PS → PL）

> **v0.2 变更**：原 v0.1 用"内存邮箱 `0x31000044` + PL 轮询请求字"，现改为
> **AXI4-Lite 寄存器触发（P 已在 `pl/rtl/ip2_axi_top.v` 实现）**。
> 理由：寄存器接口更规范、地址与帧号可配置，且不需要 PL 额外轮询内存。
> **P 的 RTL 当前不含内存邮箱，本版无需修改 RTL。**

### 3.1 AXI4-Lite 寄存器表（P 实现，v0.2 确认）

**基地址：`0x83C00000`（256 KB）** —— ⚠️ 待 P 在板上确认该段可用
（我不便代查 `/proc/iomem`，板子在 P 手上）。

**已知不可用的段（务必避开）：**

| 地址段 | 占用者 |
|---|---|
| `0x30100000 ~ 0x38100000` | udmabuf 保留区（帧 + 结果都在里面）|
| `0x40000000 ~ 0x400000E3` | AI_Mate 寄存器窗口 |
| `0x400C0000 ~ 0x400FFFFF` | custom op 空间（官方预留）|

**寄存器定义：**

| 偏移 | 名称 | 方向 | 含义 |
|---|---|---|---|
| **`0x00`** | **CTRL** | W | **写 1 启动本帧处理**（start），PL 处理完自动清零 |
| `0x04` | FRAME_ADDR | W | 输入帧物理地址（默认 `0x30100000`）|
| `0x08` | RESULT_ADDR | W | 输出区物理地址（默认 `0x31000000`）|
| `0x0C` | STATUS | R | `busy` \| `done` \| `error` \| `n_cand` \| 帧计数 |
| `0x10` | FRAME_ID | W | 帧号（低 16 位，会被写进状态字回传）|
| `0x14` | VERSION | R | `0x0001_0000`（v1.0）|

### 3.2 按帧触发流程（PS 侧）

PL 不做连续自由运行，按帧触发，避免与 PS 写下一帧冲突：

1. PS 把第 k 帧灰度图写入 `0x30100000 + (k mod 72) × 230400`；
2. PS 做 `sync_for_device`（**必须**，`dma_coherent=0`，见 §4）；
3. PS 写 `FRAME_ADDR` / `RESULT_ADDR`（首次或地址变化时），写 `FRAME_ID = k`；
4. **PS 写 `CTRL = 1` 启动**；
5. PS 轮询 `STATUS.done`，或读状态字 `bit31`（§2.2）；
6. PS 做 `sync_for_cpu` → 读 36 B 候选表。

**⚠️ 待 P 确认的一个细节**：`CTRL=1` 是否"每帧都要写一次、PL 处理完自动清零"？
如果是，PS 侧就不需要 v0.1 里那套 `bit16` 翻转判据（那是内存邮箱方案的产物）。

**PS 侧实现**：`ps/pl_link.py`（已入库），`_reg_write()` 留 TODO 等基地址与访问方式
（`/dev/mem` 还是 `/dev/uioN`）确定后填入。

## 4. 缓存一致性流程（`dma_coherent=0`，必须做）

**PS 写帧之后、写邮箱之前：**

```sh
echo $((k*230400)) > /sys/class/u-dma-buf/udmabuf0/sync_offset
echo 230400        > /sys/class/u-dma-buf/udmabuf0/sync_size
echo 1             > /sys/class/u-dma-buf/udmabuf0/sync_for_device
```

**PS 读结果之前：**

```sh
echo 0    > /sys/class/u-dma-buf/udmabuf0/sync_offset   # 输出区起点 = 0x31000000
echo 44   > /sys/class/u-dma-buf/udmabuf0/sync_size
echo 1    > /sys/class/u-dma-buf/udmabuf0/sync_for_cpu
```

⚠️ 不 sync 的现象是"随机帧结果错"，极难定位（看起来像逻辑 bug）。
⚠️ `CONFIG_STRICT_DEVMEM` 开着 → `/dev/mem` 访问 `0x30100000` 会被拒绝（`Operation not permitted`），不要试图用 `/dev/mem` 验证地址，只能走完整闭环。

### 6.1 已知风险：100 MHz 域的时序从未被分析

已出的两份位流的时序报告里，Procise 只分析了 `sys_clk`（200 MHz 主时钟，**只有 1 个端点 = 分频寄存器本身**，WNS 4.471 ns），**由 ÷2 分频得到的 100 MHz 工作时钟域完全没有约束、没有分析**。

- 上板现象：`ip2_board_top` 的 4 个 LED 全常亮（`led[3:1]=111` → `ncand ≥ 7`），与仿真「ncand = 4、`led = 1000`」不符；
- 首要嫌疑：CFAR 改真实 std 后判决路径是「31 输入加法树 → 11×26 与 18×18 乘法 → 40 bit 比较」单周期组合，很可能远超 10 ns；
- 处置：在 `pl/constr/board_lite.fdc` 里补
  `create_generated_clock -name clk100 -source [get_ports {clk_p}] -divide_by 2 [get_pins {u_bufg100/O}]`
  重新 place/route 拿到 100 MHz 域的真实 WNS；若为负，再决定「插流水」还是「把工作时钟降到 50 MHz」。
- 现状：`create_generated_clock` 已写进 `pl/constr/board_lite.fdc`，配套脚本 `synth/board_ip2_timing.tcl`（出一份**带时序约束**的 `ip2_board_top_t.bit`），等一次 place/route 验证。
- 已确认无关的项：位流下载链路本身是通的（`blink_top.bit` 上板三颗 LED 按设计频率闪烁、`ip2_board_top.bit` 能烧进去），所以 LED 现象不是下载问题，而是数据/时序问题。

| 4 | **同步责任** | **无异议**，`sync_for_device` / `sync_for_cpu` 全部由 PS 侧负责，PL 不涉及 cache |
| 5 | **候选表 `x,y` 语义** | **质心**（P 的实现正确）。依据：`baseline/detect_v1.py:extract_candidates` 直接取 `cv2.connectedComponentsWithStats` 的质心输出 `cents[i]`。此前 `docs/13` 笼统写"坐标"未指明语义，已更正 |
