## 1. 帧缓冲区（板载 U-DMA-BUF，实测确认）

| 项 | 值 |
|---|---|
| 设备节点 | `/dev/udmabuf0`（char 242:0） |
| 物理基址 | **`0x30100000`** |
| 总容量 | 128 MiB（134,217,728 B） |
| 驱动 | ikwzm u-dma-buf 3.2.5 |
| sysfs | `/sys/class/u-dma-buf/udmabuf0/` |
| `sync_mode` | 1（可按 offset/size 局部同步） |
| `dma_coherent` | **0（非缓存一致，必须手动 sync）** |
| 一帧大小 | **230,400 B**（640×360 灰度，8 bit/像素） |
| 第 k 帧地址 | `0x30100000 + k × 230400` |
| 内存归属 | `/proc/iomem` 的 `2fded000-3fffffff` reserved 区（官方给 PL/DMA 留的 258 MB） |

### 1.1 128 MiB 分区

| 区间 | 大小 | 用途 |
|---|---|---|
| `0x30100000` ~ `0x30FFFFFF` | 16 MiB | **输入帧区**（PS 写 / PL 读），72 帧 |
| `0x31000000` ~ `0x310FFFFF` | 1 MiB | **输出区**（PL 写 / PS 读） |
| `0x31100000` ~ `0x380FFFFF` | 111 MiB | 备用（多缓冲 / 中间结果） |

## 2. 输出区布局（PL 写）

| 偏移 | 长度 | 内容 |
|---|---|---|
| `0x31000000` + 0 | 36 B | **候选表**（见 §2.1） |
| `0x31000040` + 0 | 4 B | **状态字**（见 §2.2） |
| `0x31000044` + 0 | 4 B | **邮箱请求字**（PS 写 / PL 读，见 §3） |

候选表与状态字放在同一 sync 区间（`sync_offset=0`、`sync_size=44`），PS 一次 sync 全看到。

### 2.1 候选表格式（36 B，PL → PS）

```
byte 0 : n_cand 候选个数
byte 1 ~ 7 : 候选 0 x_hi, x_lo, y_hi, y_lo, 0, area, peak
byte 8 ~ 14 : 候选 1 （同上，7 字节/候选）
byte 15 ~ 21 : 候选 2
... : （每候选 7 字节，按 peak 降序连续排布）
```

两种配置（ 2026-10-30 更正：原 v0.5 写的 `0x40/0x44` 是错的，见下）：

| 配置 | 候选上限 | 字节数 | 读取方式 | 状态 |
|---|---|---|---|---|
| **兼容视图** | 5 | 36 B（1 + 5×7） | AXI-Lite `0x18~0x38`（9 个 32 位字，`legacy_ram[0..8]`）| 已实测 |
| **完整视图** | **64** | **452 B**（1 + 64×7，113 个 32 位字）| **AXI-Lite `0x10` 索引窗口** | 已实测 |

 权威依据：`docs/23-寄存器映射与候选表窗口.md`（P 维护，唯一权威）。以下为摘要。

### 2.1.1 候选表窗口的正确用法（`0x10`，不是 `0x40/0x44`）

```
0x10 写 = 设"字索引"（0 ~ 112）
0x10 读 = 取该索引对应的 32 位字
⇒ 必须严格「写索引 → 读数据」配对，中间不能插别的寄存器写
```

读取 64 个候选（113 字）的流程：

```python
for i in range(113): # 0..112
 wr(0x10, i) # 设索引
 word = rd(0x10) # 取该字（注意：同址读写，含义不同）
 buf[4*i : 4*i+4] = word.to_bytes(4, "little")
n_cand = buf[0]
cands = [decode(buf[1+7*k : 8+7*k]) for k in range(min(n_cand, 64))]
```

### 2.1.2 两个需要记住的坑

坑 1：`0x40` 会绕回 `0x00`（6 位地址）

```
总线是 s_axi_awaddr[5:0]，所以：
 写 0x40 → 实际写 0x00 = 误触发一帧（start）
 读 0x44 → 实际读 0x04 = 读回 frame_addr（0x30100000）
```

⇒ 早期文档写的「窗口在 `0x40/0x44`」来自一版已回退的 8 位地址实验分支，现在一律用 `0x10`。

**⇒ 按 `0x40/0x44` 写代码的后果：每读一个字就误触发一帧（PL 白跑 10 ms），而且读回来的是 `frame_addr` 而非候选数据 —— 表面症状就是"候选表是垃圾 / 只读到 5 个"。**

坑 2：同址读写语义不同

⇒ `0x10` 写=设索引、读=取数据。若中间插了别的寄存器写，索引会被改，之后读的全是错行。

### 2.1.3 视图自动判定（不写任何寄存器）

```
索引复位默认为 0，因此：
 rd(0x10) == rd(0x18) → 有索引窗口（新构建），可用 113 字 / 64 候选否则 → 老构建（如 A 的合并位流，6 位地址且无窗口），
 退化为 0x18 起 36 字节兼容视图
```

**⇒ 判定过程**不写任何寄存器，避免把老构建里 `0x10`（可能是别的语义）写坏。

⇒ 参考实现：`ps/cand_read.py --view auto`（P 已统一 7 个脚本的常量来源）。

> **教训（P 的 docs/23 原话）：地址常量只能有一个来源。后续任何寄存器改动，先改 `docs/23`，再改 `cand_read.py`，其它脚本一律复用它。**

- `x`、`y`：16 bit 大端（`x_hi` 在前），**连通域质心坐标**，单位为 640×360 降采样后的像素
 - 语义依据：`baseline/detect_v1.py:extract_candidates` 直接取 `cv2.connectedComponentsWithStats` 的质心输出 `cents[i]`；PL 侧 `candidate_extract.v` 同为 8 连通 CCL 质心计算 —— 三方一致
 - 历史勘误：本文档 v0.1~v0.3 曾在此处写「左上角坐标」，错误。§7 第 5 条已澄清为质心
- `byte 4`：预留（原 area 高字节位置）；2026-10-29 起 area 已扩到 16 位，见下
- `area`：**16 bit**（v0.6 起，原 8 bit 装不下大目标：20px 目标面积 400、30px 900）；过滤范围改为 `[2, 2047]`
- `peak`：8 bit 连通域内增强图最大值
- 候选按 `peak` **降序**排列；上限 64 个；不足则在 `n_cand` 之后填 0

#### 2.1.1 质心精度验收指标（2026-10-26 新增）

下游级联判别的 ROI 裁剪以该质心为中心，因此质心误差直接决定判别命中率。经验证实验标定：

| 质心偏移 | ROI 判别命中率 | 说明 |
|---|---|---|
| ±0 px（真值中心）| 91%~95% | 上限参考 |
| **±16 px** | **无影响** | 与真值中心持平 |
| **±32 px** | **≥85%** | 仍可用 |

- 偏移量单位为原图 1280×720 的像素；±32 px 相当于原图宽度的 5%
- 结论：PL 粗筛输出的质心误差应控制在 ≤32 px（5%）以内；±16 px 以内无精度损失
- 机理：64×64 的 ROI 对 15-35px 目标完整率 100%、目标占比 47%（实测），既完整容纳目标又保留判别所需的局部上下文
- 若粗筛误差超过 32 px，需评估是否加大 ROI 边长，或依赖时域确认与多帧关联补偿

#### 2.1.2 ROI 裁剪边长（v0.5 改版：448 单块 → 64×64 网格）

**变更背景：** 原方案为「每候选裁 448×448，letterbox 到 320 后拼 2×2 网格」，但覆盖 64 个候选需 16 次前向，太慢。2026-10-28 改为「每候选裁 64×64，拼 8×8 = 512×512 网格，一次前向判完 64 个」。

| 项 | 约定（v0.5） |
|---|---|
| **裁剪方式** | 以质心为中心，**固定边长 64 px**（越界补 0 或推回贴边）|
| **网格拼装** | 行优先 `k = 行×8 + 列`，8×8 = 64 格，画布 512×512 灰度，灰度复制三通道后送 NPU |
| **执行位置** | **PS 侧** —— 实测 64 个 64×64 拼 8×8 仅 **0.09 ms**（加灰度复制三通道 0.46 ms），PL 不做裁剪 |
| **几何依据** | ROI 64×64 对 15-35px 完整率 **100%**、目标占比 47.3%；对 35-70px 完整率 **96%**、占比 69.4%（100 张真实图实测）|
| **召回依据** | 粗筛按 peak 截 top-64 时召回 **85.0%**（15-35px 档 80.0%、70-150px 档 92.0%）|
| **已取消** | `pl/rtl/roi_pack.v` **不需要改 448，也不需要流式化** —— 裁剪已移至 PS。该模块可保留作可选加速，不属必需路径 |
| ** 已知局限** | 70-150px 在 64×64 格里完整率仅 3.3%；大目标需走「按面积分流」（大目标用全图检测）或加大 ROI |

> 为什么裁剪放 PS 不放 PL： 实测 PS 拼网格 0.09 ms（64 格）/ 0.03 ms（16 格），而 PL 做同样的事需要 57 块 BRAM 做帧缓冲（128×128×16）。把裁剪留给 PS 既省 PL 资源，又不构成性能瓶颈（端到端瓶颈在 NPU）。

### 2.2 状态字（4 B，PL → PS）

| bit | 含义 |
|---|---|
| 31 | `done`：本帧处理完成（PL 置 1） |
| 30 | `error`：AXI 读超时/异常（PL 置 1） |
| 29:16 | 保留（0） |
| 15:0 | `frame_id`：本次处理的帧号（与邮箱请求字一致，取低 16 位） |

PL 在开始处理新帧时把 `done` 清 0，处理完置 1 → PS 用 `done` 上升沿判断可取结果。

### 2.3 地址归属与冲突（重要）

| 地址段 | 归属 | 本设计能否用 |
|---|---|---|
| `0x40000000 ~ 0x400000E3` | **AI_Mate（NPU）寄存器窗口**，实测 224 B | 见下「两种位流」 |
| `0x80000000` | **AI_Mate 的 DMA 窗口**（`--backends "...&dma=0x80000000"`） | 见下 |
| `0x30100000`（udmabuf 128 MiB） | 输入帧 + 输出区 | 本设计的 AXI 主口读写目标 |
| **`0x43C00000`（建议 256 KB）** | **本设计 AXI4-Lite 从口**（控制/状态寄存器） | 建议分配，和上面两段都不重叠 |

### 2.3.1 两种位流下的地址行为完全不同（2026-10-30 实测补充）

| 位流 | `0x40000000` 与 `0x43C00000` | NPU 可用？ | 说明 |
|---|---|---|---|
| **P 的自研位流**（只有 IP2）| **完全别名**（实测 4 对地址全等）| 不存在 | SmartConnect 单主单从不做地址译码，两个窗口落到同一处 |
| **A 的合并位流**（IP2 + AI_Mate）| **不别名**（`0x4000001C = 0x25122301`，是真正的 AI_Mate 版本号）| 寄存器通、**DMA 断** | A 做了地址译码；但他为规避 fmsh 器件补丁剪掉了 PS7 上 3907 个 AI 引脚，`M_AI_HP` DMA 通路随之断开 → `forward()` 悬挂、整板卡死 |

⇒ 判据：读 `0x4000001C`。
- 若 == `0x25122301` → 是 A 的合并位流，NPU 寄存器可见（但 DMA 可能不通）
- 若 == 候选表数据/`0x43C0001C` 的值 → 别名，说明在当前是 P 的自研位流

⇒ `ps/npu_smoke.py` 已内置这个判据（先探再建会话）。

 历史记录（2026-10-28 时点的判断，已被上表取代）：
- 曾判断「PL 与 NPU 不能共存（同一时刻只有一份位流）」—— A 的合并位流已经打破这一限制，IP2 数据通路**逐位无损**（`VERSION=0x00010000`、候选坐标/面积/峰值全对）。
- 当时的方案是「两套位流分别演示、报告里说明两种工作模式」。**现在升级为：合并位流已存在，唯一阻塞是 NPU 的 DMA 通路（A 侧引脚裁剪，需换 IP_PATCH 版本或找复旦微 FAE）。**

 `0x40000000` 和 `0x80000000` 在 `/proc/iomem` 里都**不是**已注册外设（是位流里的 AXI 从设备/窗口），所以"读全 F"或"读 0xAA"都不能证明它没被用——以功能实测为准。

## 3. 触发与寄存器接口（PS → PL）

> **v0.2 变更**：原 v0.1 用"内存邮箱 `0x31000044` + PL 轮询请求字"，现改为
> AXI4-Lite 寄存器触发（P 已在 `pl/rtl/ip2_axi_top.v` 实现）。
> 理由：寄存器接口更规范、地址与帧号可配置，且不需要 PL 额外轮询内存。
> P 的 RTL 当前不含内存邮箱，本版无需修改 RTL。

### 3.1 AXI4-Lite 寄存器表（P 实现，v0.2 确认）

基地址：`0x43C00000`（256 KB） —— 待 P 在板上确认该段可用
（我不便代查 `/proc/iomem`，板子在 P 手上）。

已知不可用的段（务必避开）：

| 地址段 | 占用者 |
|---|---|
| `0x30100000 ~ 0x38100000` | udmabuf 保留区（帧 + 结果都在里面）|
| `0x40000000 ~ 0x400000E3` | AI_Mate 寄存器窗口 |
| `0x400C0000 ~ 0x400FFFFF` | custom op 空间（官方预留）|

**寄存器定义：**

| 偏移 | 名称 | 方向 | 含义 |
|---|---|---|---|
| **`0x00`** | **CTRL** | W | **写 1 启动本帧处理**（start），PL 处理完自动清零 |
| `0x04` | FRAME_ADDR | W | 输入帧物理地址（默认 `0x30100000`）|
| `0x08` | RESULT_ADDR | W | 输出区物理地址（默认 `0x31000000`）|
| `0x0C` | STATUS | R | `busy` \| `done` \| `error` \| `n_cand` \| 帧计数 |
| `0x10` | FRAME_ID | W | 帧号（低 16 位，会被写进状态字回传）|
| `0x14` | VERSION | R | `0x0001_0000`（v1.0）|

### 3.2 按帧触发流程（PS 侧）

PL 不做连续自由运行，按帧触发，避免与 PS 写下一帧冲突：

1. PS 把第 k 帧灰度图写入 `0x30100000 + (k mod 72) × 230400`；
2. PS 做 `sync_for_device`（**必须**，`dma_coherent=0`，见 §4）；
3. PS 写 `FRAME_ADDR` / `RESULT_ADDR`（首次或地址变化时），写 `FRAME_ID = k`；
4. PS 写 `CTRL = 1` 启动；
5. PS 轮询 `STATUS.done`，或读状态字 `bit31`（§2.2）；
6. PS 做 `sync_for_cpu` → 读 36 B 候选表。

 待 P 确认的一个细节：`CTRL=1` 是否"每帧都要写一次、PL 处理完自动清零"？
如果是，PS 侧就不需要 v0.1 里那套 `bit16` 翻转判据（那是内存邮箱方案的产物）。

**PS 侧实现**：`ps/pl_link.py`（已入库），`_reg_write()` 留 TODO 等基地址与访问方式
（`/dev/mem` 还是 `/dev/uioN`）确定后填入。

## 4. 缓存一致性流程（`dma_coherent=0`，必须做）

PS 写帧之后、写邮箱之前：

```sh
echo $((k*230400)) > /sys/class/u-dma-buf/udmabuf0/sync_offset
echo 230400 > /sys/class/u-dma-buf/udmabuf0/sync_size
echo 1 > /sys/class/u-dma-buf/udmabuf0/sync_for_device
```

**PS 读结果之前：**

```sh
echo 0 > /sys/class/u-dma-buf/udmabuf0/sync_offset # 输出区起点 = 0x31000000
echo 44 > /sys/class/u-dma-buf/udmabuf0/sync_size
echo 1 > /sys/class/u-dma-buf/udmabuf0/sync_for_cpu
```

 不 sync 的现象是"随机帧结果错"，极难定位（看起来像逻辑 bug）。
 `CONFIG_STRICT_DEVMEM` 开着 → `/dev/mem` 访问 `0x30100000` 会被拒绝（`Operation not permitted`），不要试图用 `/dev/mem` 验证地址，只能走完整闭环。

## 5. 时序与性能预算

> ### v0.2 重要警示：本节的 4.9 ms/帧 暂按「待时序确认」看待
>
> P 在 2026-10-23 反馈：**已出位流的时序报告里，Procise 只分析了 `sys_clk`
> （200 MHz 主时钟，且只有 1 个端点），由 ÷2 得到的 100 MHz 工作时钟域
> 从未被约束、没被分析。**
>
> **更严重的现象**：板上跑自测图案时 LED 显示的候选数饱和到 7（仿真应为 4）。
>
> 2026-10-25 更新 —— LED 现象的根因已定位为两层：
>
> | 层 | 原因 | 状态 |
> |---|---|---|
> | **① 功能 bug** | `cand_buf`（36 B 候选表）在 `F_WRITE` 状态被 `chain_rst_n` 误清零 → 数据被破坏 | **已修复**（P 提交 `a69adc0`，仿真 `VERDICT AXI-TOP-OK`，候选表与 Python 参考完全一致）|
> | **② 时序风险** | 100 MHz 工作域在**已发布位流**里从未被约束；CFAR 改"真实 std"后判决路径是「31 输入加法树 → 11×26 与 18×18 乘法 → 40 bit 比较」单周期组合，很可能远超 10 ns | **仍未验证**（仓库内 `board_lite.fdc` 只有 1 条 `create_clock`）|
>
> ⇒ 所以 "LED=7" 不再单纯归因于超时。但要确认功能层修复在真板上生效，仍必须先把时序约束补上、拿到 WNS，否则无法区分"修好了"和"碰巧对了"。
>
> ⇒ 在时序约束补齐、`place/route` 重跑并确认 WNS ≥ 0 之前：
> - 本节所有性能数字**不可引用**
> - PL 计算结果**不可信**，不能用于演示或报告
> - 与 NPU 共存、上板联调**均无意义**（错的逻辑放进更大的位流还是错的）
>
> **⇒ 处理要求**：补 `create_generated_clock`（100 MHz 域）+ 所有 IO 的
> `input/output delay` → 重跑 place/route → 若 WNS < 0，**宁可将主频降到 50 MHz
> 也要把时序压正（时序不收敛时宁可降频，变慢也远比算错强）→ 2026-10-26 已解决**：降到 50 MHz 后 setup +0.041 ns，LED 候选数 = 4，与仿真一致。

### 6.1 已知风险：100 MHz 域的时序从未被分析已出的两份位流的时序报告里，Procise 只分析了 `sys_clk`（200 MHz 主时钟，只有 1 个端点 = 分频寄存器本身，WNS 4.471 ns），由 ÷2 分频得到的 100 MHz 工作时钟域完全没有约束、没有分析。

- 处置：在 `pl/constr/board_lite.fdc` 里补
 `create_generated_clock -name clk100 -source [get_ports {clk_p}] -divide_by 2 [get_pins {u_bufg100/O}]`
 重新 place/route 拿到 100 MHz 域的真实 WNS；若为负，再决定「插流水」还是「把工作时钟降到 50 MHz」。
- 现状：`create_generated_clock` 已写进 `pl/constr/board_lite.fdc`，配套脚本 `synth/board_ip2_timing.tcl`（出一份**带时序约束**的 `ip2_board_top_t.bit`），等一次 place/route 验证。
- 已确认无关的项：位流下载链路本身是通的（`blink_top.bit` 上板三颗 LED 按设计频率闪烁、`ip2_board_top.bit` 能烧进去），所以 LED 现象不是下载问题，而是数据/时序问题。
