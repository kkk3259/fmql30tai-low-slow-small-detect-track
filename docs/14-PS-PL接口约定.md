# 14 · PS ↔ PL 接口约定（草案 v0.1）

> 维护：P（PL）｜ 对接：S（PS/应用）
> 依据：S 2026-10-23 实测的 U-DMA-BUF 参数（帧缓冲区实测确认）
> 状态：**待 S 确认**，确认后 PL 侧按此实现 AXI Master，PS 侧按此实现收发。

## 1. 帧缓冲区（板载 U-DMA-BUF，实测确认）

| 项 | 值 |
|---|---|
| 设备节点 | `/dev/udmabuf0`（char 242:0） |
| 物理基址 | **`0x30100000`** |
| 总容量 | 128 MiB（134,217,728 B） |
| 驱动 | ikwzm u-dma-buf 3.2.5 |
| sysfs | `/sys/class/u-dma-buf/udmabuf0/` |
| `sync_mode` | 1（可按 offset/size 局部同步） |
| `dma_coherent` | **0（非缓存一致，必须手动 sync）** |
| 一帧大小 | **230,400 B**（640×360 灰度，8 bit/像素） |
| 第 k 帧地址 | `0x30100000 + k × 230400` |
| 内存归属 | `/proc/iomem` 的 `2fded000-3fffffff` reserved 区（官方给 PL/DMA 留的 258 MB） |

### 1.1 128 MiB 分区

| 区间 | 大小 | 用途 |
|---|---|---|
| `0x30100000` ~ `0x30FFFFFF` | 16 MiB | **输入帧区**（PS 写 / PL 读），72 帧 |
| `0x31000000` ~ `0x310FFFFF` | 1 MiB | **输出区**（PL 写 / PS 读） |
| `0x31100000` ~ `0x380FFFFF` | 111 MiB | 备用（多缓冲 / 中间结果） |

## 2. 输出区布局（PL 写）

| 偏移 | 长度 | 内容 |
|---|---|---|
| `0x31000000` + 0 | 36 B | **候选表**（见 §2.1） |
| `0x31000040` + 0 | 4 B | **状态字**（见 §2.2） |
| `0x31000044` + 0 | 4 B | **邮箱请求字**（PS 写 / PL 读，见 §3） |

候选表与状态字放在同一 sync 区间（`sync_offset=0`、`sync_size=44`），PS 一次 sync 全看到。

### 2.1 候选表格式（36 B，PL → PS）

```
byte 0        : n_cand     候选个数（0 ~ 5）
byte 1  ~ 7   : 候选 0      x_hi, x_lo, y_hi, y_lo, 0, area, peak
byte 8  ~ 14  : 候选 1      （同上，7 字节/候选）
byte 15 ~ 21  : 候选 2
byte 22 ~ 28  : 候选 3
byte 29 ~ 35  : 候选 4
```

- `x`、`y`：16 bit 大端（`x_hi` 在前），**左上角坐标，单位为 640×360 降采样后的像素**
- `byte 4`：预留恒 0（原 area 高字节位置）
- `area`：8 bit 连通域面积（像素数），范围过滤 `[2, 200]`
- `peak`：8 bit 连通域内增强图最大值
- 候选按 `peak` **降序**排列，最多 5 个；不足则 `n_cand` 之后填 0

### 2.2 状态字（4 B，PL → PS）

| bit | 含义 |
|---|---|
| 31 | `done`：本帧处理完成（PL 置 1） |
| 30 | `error`：AXI 读超时/异常（PL 置 1） |
| 29:16 | 保留（0） |
| 15:0 | `frame_id`：本次处理的帧号（与邮箱请求字一致，取低 16 位） |

PL 在开始处理新帧时把 `done` 清 0，处理完置 1 → PS 用 `done` 上升沿判断可取结果。

### 2.3 地址归属与冲突（重要）

| 地址段 | 归属 | 本设计能否用 |
|---|---|---|
| `0x40000000 ~ 0x400000E3` | **AI_Mate（NPU）寄存器窗口**，实测 224 B | ❌ **绝对不能用** |
| `0x80000000` | **AI_Mate 的 DMA 窗口**（`--backends "...&dma=0x80000000"`） | ❌ 合一位流时不能用 |
| `0x30100000`（udmabuf 128 MiB） | 输入帧 + 输出区 | ✅ 本设计的 AXI 主口读写目标 |
| **`0xA0000000`（建议 256 KB）** | **本设计 AXI4-Lite 从口**（控制/状态寄存器） | ✅ 建议分配，和上面两段都不重叠 |

⚠️ **PL 与 NPU 不能共存**（同一时刻只有一份位流在跑）：
- 本设计的位流替换官方位流后，NPU（AI_Mate）就不存在了，`0x40000000` 也不再响应；
- 反过来，官方位流里也没有我们的 IP2；
- 要共存只有一条路：在 Procise 里把 `AI_Mate.edif`（及它需要的 DDR3 MIG / AXI 互联）当黑盒例化进我们的顶层 —— 属于"从零重建"，暂不做；
- 答辩层面两套位流可以分别演示、分别录屏，报告里说明"两种工作模式"即可。

⚠️ `0x40000000` 和 `0x80000000` 在 `/proc/iomem` 里都**不是**已注册外设（是位流里的 AXI 从设备/窗口），所以"读全 F"或"读 0xAA"都不能证明它没被用——以功能实测为准。

## 3. 触发协议（PS → PL）

PL 不做连续自由运行，而是**按帧触发**，避免与 PS 写下一帧冲突。

### 3.1 方案 A（默认，**当前 RTL 已实现**）：AXI4-Lite 控制寄存器

AXI4-Lite 从口基址建议 `0xA0000000`（见 §2.3），寄存器为**该基址内的字节偏移**：

| 偏移 | 名称 | 读写 | 含义 |
|---|---|---|---|
| `0x00` | `CTRL` | W | `bit0 = start`：写 1 启动一帧（自清） |
| `0x04` | `FRAME_ADDR` | W | 输入帧物理地址（默认 `0x30100000`） |
| `0x08` | `RESULT_ADDR` | W | 输出区物理地址（默认 `0x31000000`） |
| `0x0C` | `STATUS` | R | `bit0` busy / `bit1` done / `bit2` error / `[15:8]` n_cand / `[23:16]` 已完成帧计数 |
| `0x10` | `FRAME_ID` | W | 帧号（低 16 位写进状态字回传给 PS） |
| `0x14` | `VERSION` | R | `0x0001_0000` |

PS 侧流程：
1. 写 `FRAME_ADDR` / `RESULT_ADDR` / `FRAME_ID`（可选，有默认值）；
2. 按 §4 做 `sync_for_device`（**必须**，`dma_coherent=0`）；
3. 写 `CTRL.bit0 = 1` 启动；
4. 轮询 `STATUS.bit1`(done)；
5. 做 `sync_for_cpu` → 读 36 B 候选表 + 4 B 状态字。

### 3.2 方案 B（备选，**当前 RTL 未实现**）：内存邮箱

PS 把请求字写到 `0x31000044`，PL 轮询该地址发现变化后启动一帧；`0x31000044` 之外的布局与方案 A 相同。

- 优点：PS 侧不需要 AXI-Lite 地址（只碰 udmabuf 一段内存）；
- 缺点：PL 要额外轮询 DDR（多一个 AXI 读事务流），且"帧号不要写成上次的值"这类约定容易踩坑；
- 若 S 更希望走这条，P 侧改 RTL 即可（改动集中在 `ip2_axi_top.v` 的触发分支）。

> 无论 A 还是 B：`0x31000040` 的状态字与 `0x31000000` 的候选表是两个方案共用的，PS 侧读结果代码不用改。

## 4. 缓存一致性流程（`dma_coherent=0`，必须做）

**PS 写帧之后、写邮箱之前：**

```sh
echo $((k*230400)) > /sys/class/u-dma-buf/udmabuf0/sync_offset
echo 230400        > /sys/class/u-dma-buf/udmabuf0/sync_size
echo 1             > /sys/class/u-dma-buf/udmabuf0/sync_for_device
```

**PS 读结果之前：**

```sh
echo 0    > /sys/class/u-dma-buf/udmabuf0/sync_offset   # 输出区起点 = 0x31000000
echo 44   > /sys/class/u-dma-buf/udmabuf0/sync_size
echo 1    > /sys/class/u-dma-buf/udmabuf0/sync_for_cpu
```

⚠️ 不 sync 的现象是"随机帧结果错"，极难定位（看起来像逻辑 bug）。
⚠️ `CONFIG_STRICT_DEVMEM` 开着 → `/dev/mem` 访问 `0x30100000` 会被拒绝（`Operation not permitted`），不要试图用 `/dev/mem` 验证地址，只能走完整闭环。

## 5. 时序与性能预算

| 项 | 值 | 说明 |
|---|---|---|
| PL 主时钟 | **100 MHz** | 板载 200 MHz 差分（C8/C7）÷2；GP/HP 上限也是 100 MHz |
| AXI 读带宽（64 bit @100 MHz） | 800 MB/s | 一帧 230,400 B ≈ **288 µs** |
| 计算 | ≈ **4.9 ms/帧** | IP2 约 0.49 M 拍（CFAR 虚拟光栅 261,300 + CCL 230,400） |
| 端到端（含 AXI） | ≈ **5.2 ms/帧** | 相对 PS 现在 57.87 ms 的 detect ≈ **11×** |
| PS 侧建议 | 双缓冲/环形 | PL 处理期间 PS 写第 k+1 帧 |

## 6. PL 侧实现计划

| 文件 | 作用 | 状态 |
|---|---|---|
| `pl/rtl/ip2_axi_master_rd.v` | AXI4 读主机：按帧地址读 230,400 B，输出 8 bit 流 + valid/ready | ✅ 已写（8 KB） |
| `pl/rtl/ip2_axi_master_wr.v` | AXI4 写主机：写 36 B 候选表 + 4 B 状态字（+0x00 / +0x40） | ✅ 已写（6 KB） |
| `pl/rtl/ip2_axi_top.v` | 顶层：AXI4-Lite 控制 + 读帧 → IP2 流式链 → 收 36 B → 写回 + LED | ✅ 已写（13 KB） |
| `pl/tb/tb_axi_top.v` | 带行为级 AXI 从机（内存模型）的仿真 | ✅ 已写（11 KB，仿真跑通） |

**第一版位流策略（分两步，降低风险）**

1. **先出 `ip2_board_top`（图案自测，无 AXI）**：验证 PL 能在板上跑起来 + LED 显示候选数（正常 = 4）。不依赖 PS 侧任何代码。—— **已综合出位流并下载到板**（2026-10-23，`ip2_board_top.bit`，LUT 42,313 / FF 19,453，BLINK 引脚验证通过）
2. **再出 `ip2_axi_top`（真数据）**：等第 1 步通过 + 本文件被 S 确认后开工，避免两边协议猜错。—— RTL 已就绪，**等 S 确认 §2.3 地址段与 §3.1 触发方式后综合**

### 6.1 已知风险：100 MHz 域的时序从未被分析

已出的两份位流的时序报告里，Procise 只分析了 `sys_clk`（200 MHz 主时钟，**只有 1 个端点 = 分频寄存器本身**，WNS 4.471 ns），**由 ÷2 分频得到的 100 MHz 工作时钟域完全没有约束、没有分析**。

- 上板现象：`ip2_board_top` 的 4 个 LED 全常亮（`led[3:1]=111` → `ncand ≥ 7`），与仿真「ncand = 4、`led = 1000`」不符；
- 首要嫌疑：CFAR 改真实 std 后判决路径是「31 输入加法树 → 11×26 与 18×18 乘法 → 40 bit 比较」单周期组合，很可能远超 10 ns；
- 处置：在 `pl/constr/board_lite.fdc` 里补
  `create_generated_clock -name clk100 -source [get_ports {clk_p}] -divide_by 2 [get_pins {u_bufg100/O}]`
  重新 place/route 拿到 100 MHz 域的真实 WNS；若为负，再决定「插流水」还是「把工作时钟降到 50 MHz」。
