## 2. 修好的两件事

### 2.1 寄存器连写会丢（软件侧规避）
`detect3d.detect()` 原来把 `0x04 / 0x08 / 0x00(0) / 0x00(1)` 四个写背靠背发出去，我们的 ra→core 中继用 toggle 握手，
两笔写间隔小于 2 个 core 周期时只认到一笔，于是 `start_req` 没置起来，整帧不启动（表现为 AR 不增长、读到上一帧的陈旧候选表）。

规避：每次写之间 `time.sleep(0.02)`，启动写后 `sleep(0.005)`。加完之后 AR 从 7218 → 10827（+3609 = 整帧），每帧都能跑起来。

> 根本解法在 RTL：把写中继从"toggle 边沿"改成"1 深 FIFO + 计数"，这样连写不丢。列为下一步。

### 2.2 `dbg_ar` 一直是 0 是我的 Python 写错，不是 RTL 错
```python
# 错：签名是 read(addr)，多传一个 4 会抛异常，被 catch 吞掉后返回 0
dev.defaultRegRegion().read(addr, 4)[0]
# 对：
dev.defaultRegRegion().read(addr) & 0xFFFFFFFF
```
改正后：`AR(0x90) = RV(0x94) = 3609`，**完全配平**，整帧 3600 行一行不少。

## 9. 第五轮（05:00~05:30）：学长寄存器 0x01 的打包格式（重要发现）

`rtl/adder_op/reg_ctrl.v:130-133`：
`erilog
else if (ra_awevent && ra_awaddr == 16'h01) begin   // RSIZE_BASE
    rbase <= ra_awdata[15:0];     // 低 16 位 = PL-DDR 基址
    rsize <= ra_awdata[31:16];    // 高 16 位 = 读多少行（64 字节/行）
end
`
`dma.v` 直接拿 `arsize` 当读循环次数：`dma_cnt0 <= arsize`，`arvalid` 一直到 `arready && dma_cnt0==0` 才撤。

**含义**：平台帧控制器需要“基址 + 行数”两个信息，通过寄存器 **0x01** 告知；我们一直只写自己的 0x04，从没写过 0x01。
这可能解释：①每次 AR 等 ~1024 拍；②第 2 帧起超时。

**待验证**：往 0x01 写 `(3600<<16)|0x1000` 后行为是否变化。
（首测脚本无输出即结束，板子未挂，原因待查——可能是 0x01 在本位流里未实现，写入无响应。）

- 那些 `31 ms` 的是 PS 侧 detect3d 自己的轮询超时，不是设备报错

### 为什么一帧会超过 240 ms？
按平台每次 AR 等 ~1024 拍算，3609 行 × 1024 = 3.7M 拍 = 18.5 ms，远小于 240 ms。
实际却跑不完 ⇒ **中途卡住**：调试快照里 `inflight = 6` 不动，说明
"已请求 6 行、响应没回来"，而发新行的条件是 `(lf_cnt + inflight) < 16`，
一旦响应断流，FIFO 灌满后就不再发新 AR，整帧停摆直到看门狗超时。

⇒ 下一步该查的是"平台为什么会停止返回行数据"，而不是继续调超时时间。
候选原因：①rvalid 撤得过早（我方在收到响应前就把 plat_arvalid_q 拉低）；②平台对同一地址重复请求去重；③16 深 FIFO 与实际回包节奏不匹配。

## 15. 补充：in-flight / 流控的量化分析

- 平台回包节奏：每次 AR ≈ 1024 拍 @200 MHz = 5.12 µs，一行 64 字节 ⇒ ≈12.5 MB/s
- 检测器取数：i_ext_valid 1 字节/拍 @50 MHz ⇒ **≈50 MB/s**
- 我们的 FIFO 只有 16 行（1024 字节），在 20 µs 内就被抽干，之后每来一行只能喂 64 拍（1.28 µs），其余时间空转
- ⇒ 不是"断流"而是"根本喂不饱"：平台侧带宽只有检测器需求的 1/4
- 结论：要么**让平台一次读更多**（一次 AR 读 4 KB 而不是 64 B），要么降低检测器的取数速率（加反压），要么**改变架构**（先把整帧攒进 PL-DDR 再让检测器连续读）

> 这条如果成立，说明三域里"实时逐像素喂"这条路本身带宽不够；
> 最实际的解法是：检测器改为从 PL DDR 直接读（保留 AXI 主口），只把结果写到寄存器 —— 也就是回到我们独立版的架构，只是挂在平台的 DDR 上。

## 16. 第十轮（07:40）：修正第九轮的带宽结论 —— 真因是**回包丢失**，不是带宽不够

先算一遍账：
- 平台 12.5 MB/s × 18.4 ms 就能送完一帧（230400 B）
- 检测器的 F_FEED 看门狗是 **240 ms**
- ⇒ 即使按平台满速慢慢喂，一帧也只需 18.5 ms，远小于 240 ms，完全跑得完

所以"带宽不够"不成立。真正的现象是**整帧停摆**（inflight=6 卡住不动）。

### 最可疑的机制：200 MHz 域的 itf_rvalid 脉冲被 toggle 合并
平台 itf_rvalid 是 200 MHz 下单周期脉冲。我们的 512 位交接用的是 toggle（一次翻转=一个事件）：

`erilog
// clk 域（200 MHz）
if (itf_rvalid) begin lin_data_c <= itf_rdata; lin_rdy_t <= ~lin_rdy_t; end
`

如果平台连续两个周期各回一行（或间隔极短），lin_rdy_t 翻两次 → 50 MHz 核只看见"翻了一次"（或看见一次边沿），
中间那一行的 512 位数据整个丢掉，而 inflight 仍然记着"发出了 6 个请求"，
于是 inflight 永远减不回去 → 达到 16 后不再发新 AR → 整帧停摆 → 240 ms 看门狗。

### 正确改法
把 200 MHz 侧的捕获改成 小 FIFO（而不是 toggle）：
`erilog
// clk 域：来一行就压进 cfifo（深度 8），永不丢
if (itf_rvalid) begin cfifo[cf_wp] <= itf_rdata; cf_wp <= cf_wp+1; cf_cnt <= cf_cnt+1; end
`
核域按需弹出。这样即使平台连发多行也不会丢。

### 代码定位（`ip2_user_op.v` L513-527）
`erilog
if (plat_arvalid_q && itf_arready) begin      // AR 握手
    plat_arvalid_q <= 1'b0; adq_rp <= adq_rp+1; adq_cnt <= adq_cnt-1;
    ret_busy <= 1'b1; pend_wd <= 10'd0;       // 标记"有一笔在等回包"
end
...
if (itf_rvalid) begin
    lin_data_c <= itf_rdata;                  // 捕获 512 位
    lin_rdy_t  <= ~lin_rdy_t;                 // toggle 通知核域（一个边沿 = 一行）
end
`
- `ret_busy` 只有在"收到回包"时才清（后续代码），一旦丢一个回包就永久卡住
- `lin_rdy_t` 用 toggle 传递，连续两拍回包会丢一行（核域只看见一个边沿）
- 而 `inflight` 在核域记着"我发过这么多行"，丢一行就永远减不回去 → 达到 16 后停发 → 240 ms 看门狗

⇒ 与推断一致。修法：clk 域加 8 深 512 位捕获 FIFO，用计数而不是 toggle 通知核域。

## 17. 第十一轮：一个重要反证 —— `rv == ar` 说明回包没丢

实测 `AR(0x90) = RV(0x94) = 3609`，**完全相等**。

这否定了第 16 节的"回包丢失"假设：如果 200 MHz 的 `itf_rvalid` 被 toggle 合并丢了，
那 `dbg_rv` 就会小于 `dbg_ar`。实际相等 ⇒ 平台回的每一行都被计数到了。

那么 `inflight` 停在 6 的解释只能是：最后 6 笔的响应是在 `feed_on` 已经落下之后才到的
（计时口径不同步），不是丢包。

⇒ 240 ms 超时的真正原因还是"整帧总耗时超过 240 ms"，而不是中途断流。
按 3609 行 × 1024 拍 @200 MHz ≈ 18.5 ms 推算不该超时，
所以平台的真实 AR 往返延迟远大于 1024 拍（可能是每笔都要过一次 DDR 仲裁，
实际几万拍）。这个量级只能靠实测：读 `0xA0`（行请求计数）随时间的变化曲线，
或直接测"单帧从 CTRL 写到 done 的真实耗时"。

## 30. 第二帧不跑的根因：F_WRITE 等一个永远不来的 wr_done

seq_test.py 连跑 4 帧实测（vs_300.png）：

```
FRAME 0  AR+=0  NOT_RUN  STATUS=0x00000501 n=5
FRAME 1  AR+=0  NOT_RUN  STATUS=0x00000501 n=5
FRAME 2  AR+=0  NOT_RUN  STATUS=0x00000501 n=5
FRAME 3  AR+=0  NOT_RUN  STATUS=0x00000501 n=5
```

4 帧候选完全相同（x=521/553/585/618 y=359 + x=375 y=173），STATUS bit0=1（busy 未清）=> FSM 卡在 F_WRITE。

根因代码（ip2_axi_top.v）：
```verilog
assign wr_start = (fst == F_WAIT) && (ocount >= N_BYTES) && !wr_busy && !wr_done;
.cand_bytes(288'd0),   // 候选表写 DDR 早已停用，但 FSM 还在等 wr_done
```
cand_bytes=0 => 写主控没有字节可写，wr_done 永不来 => F_WRITE 里等 1e6 拍后超时 => busy 不清 => 下一帧启动被忽略。

修法：F_WRITE 直接判完成（候选表走寄存器窗口，本就不需要写 DDR）：
```verilog
F_WRITE: begin
    done_flag <= 1'b1;
    frm_cnt   <= frm_cnt + 8'd1;
    fst       <= F_FIN;
end
```

仿真回归（tb_user_op_line.v）：`PUSHED=3072 请求行=61 AR=57 RV=57 WD=0`、`VERDICT LINE-OK`，与改前一致。

### 为什么这一改动能消掉一整类怪现象
| 现象 | 解释 |
|---|---|
| 每次测图都要重载位流 | 重载=硬复位，FSM 回起始态 |
| 连跑两次结果不同 | 第一次跑完卡死，第二次读的是第一次的表 |
| 之前“x 坐标乱” | 有几次读到的是上一张图的结果 |
