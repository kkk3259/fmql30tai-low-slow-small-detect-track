### 卡点 2：PS↔PL 数据通路（这是我接下来一个月的主战场，需要你先定接口）

我的 IP2 现在是**纯流式核**：`i_data[7:0] + i_valid + i_ready → o_data[7:0] + o_valid`，**没有任何 AXI 接口**。要接到 detect 里必须二选一：

- **A. AXI4-Stream + DMA**（推荐，吞吐高）：PL 侧包一层 AXI4-Stream，PS 侧用 AXI DMA（或你们的 CDMA）把一帧 DDR 数据推给 PL，接收端收回 36 字节候选表。
- **B. AXI4-Lite 寄存器 + PL 直接读 DDR**：PL 侧做 AXI Master 读帧、写结果。

**需要你给我的接口约定**（缺一个我都写不了）：

1. 输入帧在 DDR 的**物理地址/怎么分配**（CMA？`/dev/mem`？dma-buf？），一帧多少字节
2. 输入格式：灰度还是彩色？行列序？stride？640×360 还是 1280×720
3. 谁触发一帧（寄存器写 1？中断？polling？），输出（36 字节）放在哪、怎么通知 PS 取
4. PS 侧 detect 的**算法参数**：✅ 已对齐（S 确认 `win=31 / k=4.0 / floor=3.0 / min-area=2 / max-area=200 / topk=5 / down=2`；硬件已从 MAD 近似改为**真实 std**，判决用平方比较 `L² > k²(A·S2−S1²)`，不开方）

## 六、2026-10-26 时序收敛记录（已从 100 MHz 降到 50 MHz）

### 6.1 为什么要降频

100 MHz 版在 `synthesize` 之后的 DRC 报 `no clock constraint`，补上生成时钟约束后才拿到**真实**时序：

```
Trr  10.000  slack -7.385     (synthesize)     ← 100 MHz 不收敛
```

place 之后 `ip2_board_top_place.json` 给出了确切的最差路径，一共两轮：

| 轮次 | 最差路径 | 级数 | slack | 根因 |
|---|---|---|---|---|
| 第 1 轮 | `u_cand/parent_reg[34][2]/CK → carea[28]_reg[12]/CE` | **391 级** | −225.8 ns | CCL 并查集 `find_root()` 在单拍内展开 64 次父指针遍历 |
| 第 2 轮 | `u_cand/pi_reg[1]/CK → cy[60]_reg[0]/D` | **104 级** | −12.2 ns | CCL 重心计算的单周期 16 位变量除法 |

### 6.2 两处改法（都保持逐位一致）

1. **求根改多周期**（`candidate_extract_stream.v`）：利用并查集不变式 `parent[x] < x`，按标签号**降序**、每拍处理一个标签，把累加量并给**父**标签，逐级汇聚到根。每拍只做 1 次 64:1 查表 + 1 个加法。
2. **除法改串行移位相减**：每个标签算 cx 用 17 拍 + 算 cy 用 17 拍，64 个标签约 2,400 拍（50 MHz 下 48 µs/帧，可忽略）。

验证口径（全部 0 差异）：`ccl` 0/36 字节、`chain` 0、`tb_ccl_equiv` 与旧全帧黄金版 **VERDICT IDENTICAL**、`cfar64` 0/4096、`cfar128` 0/9216、`tophat` 186（OpenCV 边界语义，未变）。

### 6.3 收敛结果（50 MHz，`board_ip2.tcl` 全程 1336 s）

```
Trr  20.000  setup slack +0.041   hold slack +0.100     ← 通过（余量很小）
LC   9,514 / 19,650 = 48.42%
LUT 20,791 站点 + LUTRAM 427,008 bit(6,672 eq) = 27,463 LUT 当量 (35.0%)
FF  10,844   BRAM 0
```

产物：`D:\FudanMicro\Procise\ip2_board_top.bit`（5,980,580 B，01:35:19）与 `.bin`（5,980,460 B，给 Linux `fpga_manager`）。

### 6.4 注意事项

- 50 MHz 下 setup 余量只有 **+41 ps**，属于"刚好过"。如果板上行为异常，优先降频：`ip2_board_top.v` 里 `div[1]` 改 `div[2]`（200÷8 = 25 MHz），同步把 `.fdc` 的 `-divide_by 4` 改 `8`。
- 帧时间随频率线性变化：**50 MHz 约 5.0 ms/帧**、25 MHz 约 9.9 ms/帧、100 MHz 约 2.5 ms/帧，仍明显快于 PS 软件 57.87 ms。
- 「LED 候选数跳到 7」的历史现象已定位为时序未收敛导致算错，不是 LED 逻辑错误。

### 8.2 卡点：像素进了链，但 CCL 一个像素都没扫到

一次 640×360 触发后的采样（`dbg_poll.py`，2026-10-28 00:5x）：

```
t=10.24ms  FST=FEED  err=0  pcount=230400=640*360   CCL.state=1(RUN)  CCL.px_cnt=0
t=...      FST=WAIT  err=4(F_WAIT 超时)             CCL.px_cnt 始终 0
```

关键推论：

- `pcount` 计的是「链主动吃掉了一个像素」（`fifo_pop = fifo_valid && ch_i_ready && chain_en`），
  说明 `i_ready` 一路为高、AXI 读主控把 230400 字节都搬进了像素 FIFO —— **PS 侧喂数没问题**。
- `candidate_extract_stream.v` 的扫描只看 `i_bin_valid`（`:99` 起），不看 `en`、也不看 CFAR 的 `sel`。
- CFAR 的 `o_valid` 来自 `q4_gate`，`i_ready` 在 `S_RUN` 且 `is_img` 时恒为高；
  而 `pcount` 推进又依赖 `ch_i_ready`（链顶层把 `cf_ready` 接成 TopHat 的 `o_ready`）——
  这两条**同时成立**是自洽的，所以问题不在握手，而在 **`cf_valid`（CFAR 输出 valid）从未置 1**。

## 九、2026-10-28 01:00~02:00 破案：候选坐标整体 +120 的根因

### 9.1 现象（上一节遗留）
板上触发一帧后，候选能出、但 **x 坐标全部 +120**（写 106/320 → 读回 226/440），
且第二次触发会混进上一帧的候选。

### 9.2 排查（三个探针，脚本都在 `repo/ps/`）
| 探针 | 做法 | 结果 |
|---|---|---|
| `shift_probe.py` | 6 个已知点（x=40 与 x=600） | 全部 +120；x=600 的点越界折到下一行 → 说明是**整帧像素流**整体平移 |
| `twice.py` | 同一图像连续触发 3 次 | 三次结果一致，**每次事务结束后帧缓冲 `level` 都固定是 120** |
| `addr_probe.py` | 只把 `FRAME_ADDR` 改成 base / base+120 / base-120 | 三次结果**完全相同** → 偏移与读地址无关 |

### 9.3 根因
`ip2_pix_fifo`（262144×8 的帧缓冲）**跨帧不清空**。
读主机每帧取走 `NPIX` 个像素、链路消费 `NPIX` 个，但事务收尾时缓冲里固定残留
**120 字节**（上一帧的最后 120 个像素）。下一帧装帧时，这 120 字节仍排在队头，
于是链路看到的第一批像素是上一帧的尾巴 → **整帧平移 120 个像素**，
并且帧尾最后 120 个像素永远读不到。因为与地址无关，所以改 `FRAME_ADDR` 无效。

### 9.4 修复（提交 `8c90339`）
1. `repo/pl/rtl/ip2_pix_fifo.v` 增加同步清空端口 `clr`：清 `wptr/rptr/count/dout_v`，
   清空期间同时屏蔽 `do_wr` 与 `fetch`（块 RAM 本体不清，只清指针计数）。
2. `repo/pl/rtl/ip2_axi_top.v`：`wire fifo_clr = (fst == F_RST) && (rstc < 5'd16);`
   —— 只在帧起始、读主机还没发出 AR 的那 16 拍清空，不丢本帧数据。
3. 同时把读长度从 `NPIX` 改为 `NPIX + 512`（读主机按 256 字节突发），
   保证整帧 `NPIX` 个像素全部到位，多余部分下一帧被 `clr` 丢掉。

### 9.5 仿真验证
`repo/pl/sim/tb_axi_top640.v` 全链 640×360 仿真，改动前后输出**逐字节一致**
（`STATUS=0x00010402`、`n_cand=4`、候选 `(106,72)(106,216)(320,72)(320,216)`），
说明本改动只影响跨帧行为，不改变单帧结果。

> 因此一直报 `diffs=19/36`。这是**测试台的参考文件配错**，与 RTL 无关，

## 十、2026-10-28 晚：相机 -> PL -> 候选表 全流程打通

### 10.1 结论（可写进文章/答辩）
- **端到端闭环成立**：USB 相机 640x480(MJPG) -> 裁剪 640x360 -> DDR 帧缓冲 -> PL(IP2) -> AXI-Lite 候选表 -> 浏览器实时叠加框。
- **实测指标**：PL 单帧 **11.7 ms**；整环 **14.9 fps**（瓶颈是 PS 侧 cv2 取图+解码 27 ms，不是 PL）。
- **坐标正确**：寄存器镜像版在板上四组用例全部命中期望坐标（(100,120)、(320,180)、(60,300)/(500,60)/(580,340)、(100,120)/(400,200)），此前的 +120 像素整体平移已随帧缓冲 clr 修复消失。

### 10.2 本轮修掉的两个真问题
1. **帧缓冲跨帧残留 120 字节**（ip2_pix_fifo 无清空口）：导致整帧像素流平移 120，候选 x 全体 +120。修法：给 FIFO 加 clr 端口，F_RST 前 16 拍清空；n_bytes 改 NPIX+512 防止最后一包悬空。
2. **候选表用 DDR 传递读不到**：PL 侧 m_awready/BRESP 行为与 PS 侧 mmap 语义不一致，/dev/mem 读 0x31000000 恒为 0（写进去的 0xAA 也读不回）。改为 **AXI-Lite 寄存器镜像 36 字节候选表（0x18~0x3C）**，绕开共享内存一致性，实测稳定。

### 10.3 环境坑（都已绕开）
- udmabuf 的 sync_for_device 默认按 **128 MiB 整块清 cache**，每帧白吃 ~20 ms；把 sync_offset/sync_size 收到 0/230400 后 PL 侧从 23.5 ms 降到 11.7 ms。
- 板上无 devmem、无内核头文件，统一用 /dev/mem + mmap 读写寄存器；/dev/mem 映射 0x30100000 会 EPERM（STRICT_DEVMEM），只能用 /dev/udmabuf0 访问帧缓冲。
- Vivado 批处理不能 create_bd_cell（[filemgmt 56-189] Failed to resolve reference），必须以 -mode gui 跑 build_bd.tcl；open_hw_manager 在 2018.2 batch 里也不存在，烧板一律走 xsct。
- 杀板上进程别用 pkill -f cam_demo.py：ssh 那条命令自带的命令行里含同样的字面量，会把自己杀掉；用 pkill -f 'cam_demo[.]py'。
