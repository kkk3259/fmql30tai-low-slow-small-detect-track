### 2.1b gamma 曲线预处理（✅ 找到了，效果最大）

思路：送 PL 之前先做幂律拉伸 `out = 255·(x/255)^γ`（γ<1 提亮暗部）。

机制：γ 把**背景的动态范围压扁**（云的明暗差被压到很小），CFAR 的 `mean + K·sd + floor` 里 `sd` 项随之变小，弱目标的局部反差相对就突出了。这不是"调亮度"，是改变了 CFAR 自适应门限的统计特性。

实测（同一 12 段测试集，`--inv both --border 24`）：

| γ | 平均召回 | 平均精确 | 候选/帧 |
|---|---|---|---|
| 1.0（原样） | 9.0% | 0.9% | 22.2 |
| 0.70 | 14.9% | 2.1% | 27.9 |
| 0.50 | 31.5% | 3.2% | 32.3 |
| 0.35 | 45.4% | 7.7% | 21.5 |
| 0.20 | 55.4% | 38.7% | 16.4 |
| 0.12 | 69.0% | 43.2% | 15.2 |
| 0.08 | **76.6%** | 54.9% | 10.6 |
| 0.05 | 66.2% | **73.2%** | 6.6 |

- γ=0.08 召回最高（76.6%），γ=0.05 精确最高（73.2%）且 F1 更好（0.70 vs 0.64）
- F1 最优区间 γ≈0.05~0.08，召回相比原样提升 **8.5 倍**，精确提升 **81 倍**

|---|---|---|

## 七、三域时序违例的根因（已查清）

`ours3d_timing.rpt` 里最差路径：

```
Slack (VIOLATED) : -0.702ns
Source: U0_ps_ai_wrap_demo/.../u_ddr_phy_wrcal/po_stg2_wrcal_cnt_reg[0]/C

`dut.u_ip2` 的 `pcount / ocount / fst / thv_cnt / cfv_cnt`：

```
T=100M  pcount=0     ocount=0    fst=2  (F_FEED 前，等 start)
T=200M  pcount=0     ocount=0    fst=2
T=300M  pcount=996   ocount=0    fst=3  thv=520   cfrdy=996

**解读**：
- 整帧 8,192 像素全部喂完（`pcount` 到 8192 后清零）。

**推论**：板上 `err=1` 不可能是功能逻辑错，最可能是**时序违例**（第七节的 WNS −0.703）。

## 十一、K/FLOOR 敏感度：RTL 仿真的代价（10-31 15:50 记录）

想用 `iverilog` 在真实测试帧上直接跑 K=1 与 K=0 对比，结论是**这条路不划算**：

- 新建 `pl/tb/tb_k_cmp.v`：整帧喂 640×360（或 320×180），`-P` 覆盖 `K/FLOOR`，
  把候选字节流写文件；配套 `tools/analyze_kcmp.py` 解码并与真值一对一匹配。
- 实测：640×360 单帧跑不完（>10 分钟未出候选），320×180 也要 >10 分钟。
  原因：整链在 50 MHz 下每像素要 2 拍以上，加 iverilog 对 31 输入加法树组合逻辑的求值开销，
  实际仿真速度约每秒几千拍 —— 一帧 640×360 约 50 万拍，等于十几分钟。
- 与之前 `tb_axi_top1080`（128×72 = 9,216 像素，1~2 分钟）对比：仿真时间随像素数线性上升，
  参数扫描（一个配置 × 12 段 × 120 帧）在 RTL 仿真上不可行。

**结论**：K/FLOOR 这类统计量要在**板上**扫（`eval_testset2.py` 一帧 10 ms，12 段 120 帧约 30 秒），
或者做 PS 侧等价模型（但要先证明与 RTL 逐位一致，之前试过并被证伪）。
仿真只用来验证“数据流通不通”，不用来做参数优化 —— 这条边界要记住。

踩到的两个测试台 bug（已修，留给以后）：
1. 喂数循环 `for (i...) begin din=mem[i]; vin=1; @(posedge clk); while(!irdy) ... end`
   —— irdy 低时像素被丢掉，因为 for 循环照样 i+1。正确写法是 `while (i<NPIX) begin
   din=mem[i]; vin=1; @(posedge clk); #1; if (irdy) i=i+1; end`（保持数据直到被接收）。
2. `-P tb.K=1` 在 PowerShell 里必须整体加引号 `"-Ptb_k_cmp.K=1"`，否则 `=` 被拆开报
   `No such file or directory`。

## 十五、三域数据通路：512→64 拆包的字节交织根因（2026-10-31 18:30）

### 现象
三域位流上板后，检测器能出候选，但 **x 坐标错乱**：真值 x=80/240/400/560 只报两簇（间距恒 320），
单个 14px 方块在 (100,150) 直接 **0 候选**（不稳定）。

### 定位手段：片上像素捕获
在 `pl/rtl/ip2_user_op.v` 里加 256 字节捕获 RAM（core 域写、ra 域读，寄存器口 0xB4 写索引 / 0xB8 读数据），
喂一张每像素值唯一的渐变图 `px(x,y)=10+((x+3y)%240)`，读回检测器实际收到的字节：

```
idx :  exp  got
  0 :   10   10     <- 对
  7 :   17   17     <- 对
  8 :   18   74     <- 74 = 第 64 个像素
 16 :   26  138     <- 138 = 第 128 个像素
```

### 根因
平台 `User_Ddr_*` 返回的 512 位不是「word0=像素0~7、word1=像素8~15」，
而是 **字节交织**：

```
第 w 个 64 位字的第 b 个字节  =  图像第 (b*8 + w) 个像素
```

所以原来 `line_word = line_data[{want_word,3'b000} +: 64]` 取到的是 8 个**跨 8 像素**的字节，
一个 512 位响应里只用掉了 1/8 的数据 → 图像被横向压缩/错位 → x 坐标乱、小目标丢失。

### 修法（已改，`ip2_user_op.v`）
第 k 个字要横向汇聚 8 个字的同一字节：

```verilog
wire [63:0] lane_gath = { line_data[{3'd7,3'b000} + lane_sel], line_data[{3'd6,3'b000} + lane_sel],
                          line_data[{3'd5,3'b000} + lane_sel], line_data[{3'd4,3'b000} + lane_sel],
                          line_data[{3'd3,3'b000} + lane_sel], line_data[{3'd2,3'b000} + lane_sel],
                          line_data[{3'd1,3'b000} + lane_sel], line_data[{3'd0,3'b000} + lane_sel] };
assign m_rdata = lane_gath;
```

### 同时修掉的 err=1
`err_code=1` 来自读主机收到的 `RRESP != OKAY`。触发点是 **冲刷拍**：读满一帧后还要多读
`512 + 32W` 字节把 CFAR/CCL 流水线顶空，这段越界读平台会回非 OKAY。
改为 `if (rd_error && !frame_loaded)` —— 帧已搬完就不再判致命。


## 十六、512→64 拆包的第二层 bug：AR 把 bus_addr 重置了（2026-10-31 19:20）

### 现象（像素捕获实测，`capdump.py`）

第一版修了「字节交织」之后重新烧板，捕获到的前 24 个字节是：

```
got[0..7]  = 10 10 10 10 10 10 10 10      <- 同一个像素重复 8 次
got[8..15] = 74 74 74 74 74 74 74 74      <- 直接跳到第 64 个像素
got[16..23]= 138 138 ...                  <- 再跳 64
```

即：每 8 拍里 8 次都取到同一行的第 0 个字，横向被压成 1/8。

### 根因

`ip2_user_op.v` 里 64 位主口的地址处理写成：

```verilog
if (m_arvalid && m_arready) bus_addr <= m_araddr;   // 每个 AR 都重装
```

主机（`ip2_axi_master_rd.v`）是 32 拍突发（`BURST=32`、`arlen=31`），但突发内的
8 拍地址要靠从机自己 +8 递增。一旦每个 AR 都把 `bus_addr` 拉回突发首地址，
同一行里的 8 个字就永远只取第 0 个。

### 修法（fix2）

```verilog
if (m_arvalid && m_arready) begin
    if (m_araddr <= bus_addr) bus_addr <= m_araddr;  // 只有地址回绕（新一帧）才重装
    bus_left   <= m_arlen;
    bus_active <= 1'b1;
end
```

判据是「地址回绕」：帧内地址单调递增，只有新一帧重新从帧首读时 `m_araddr` 才会小于当前
`bus_addr`。

### 验证方法

`capdump.py` 喂一张每个像素值都唯一的渐变图，读回前 256 个字节。
修复后的期望结果：`10 11 12 13 ...` 连续（或 `10 18 26 ...` 跳 8，取决于平台交织方式，
两种都能解释，只要单调且不重复）。

### 教训

1. 「从机自己递增地址」和「主机每拍给地址」是两种协议，混用必错；写适配层时要先确认主机
   到底给不给每拍地址。
2. 只有像素级捕获（0xB4/0xB8）能在 30 秒内定位这类问题；靠坐标反推要多烧 3~4 次位流。

## 十八、NPU 输出回读的绑定层死路（2026-10-31 22:40，板上实测）

### 结论

NPU **算得出来**（cls128_drone 121 ops、apply 704 ms、forward **0.68 ms**），
但从 Python **拿不回结果**。四条路全试过：

| 接口 | 结果 |
|---|---|
| `np.array(output[0])` | 进程直接崩 `terminate called after throwing icraft::InternalError` |
| `output.read(bytearray, 0, n)` | `InternalError` + C++ 栈回溯 |
| `output.copyData(memchunk)` | `TypeError`（签名只收 buffer） |
| `output.to(host_memregion)` | `InternalError` |
| `host_tensor.copyFrom(0, out, 0, 8)` 再 `read()` | copyFrom 不报错但**值恒为 0**，再 `read` 又 `InternalError` |
| `sess.forward(inputs, outputs)` 双参数 | `InternalError` |

### 根因

板上的 ICraft 运行时是 **3.33.1**（`icraft`/`customop` 两个 deb），而
`/usr/local/lib/python3.8/dist-packages/icraft/` 里的 Python 包本体（`__init__.py` 等）是 3.39。
把 `.so` 换成 3.33 后 `import` 与 `forward` 能跑，但**张量内存拷贝**这部分 ABI 对不上。

### 正确出路：C++

板上环境齐全（已验证）：

```
/usr/include/icraft-xrt/core/{device,session,tensor,backend}.h
/usr/lib/aarch64-linux-gnu/libicraft_{xrt,xir,utils,zg330backend}.so
g++ 9.4.0
```

头文件里已确认的接口：

```cpp
static Session CreateWithBackends(const NetworkView&, const std::vector<Backend>&);
void apply();
std::vector<Tensor> forward(const std::vector<Tensor>& inputs);
void forward(const std::vector<Tensor>& inputs, const std::vector<Tensor>& outputs);
void Tensor::read(char* dest, uint64_t src_offset, uint64_t byte_size) const;
void Tensor::copyFrom(uint64_t dst_off, const Tensor&, uint64_t src_off, uint64_t n);
```

C++ 端的 `Tensor::read` 是原生接口，不存在 Python 桥的版本问题。

### 今晚没解决的部分（诚实记录）

NPU 的**输入**送得进去（灰度裁剪 128×128×3 NHWC uint8），**前向有结果**（0.68 ms），
但**结果读不回来**。所以"用 NPU 判定候选框"这一步**尚未形成闭环**，
只能证明「NPU 有这个能力、且我们的模型能在上面跑」。


## 十九、NPU 判定级联接通（2026-10-31 21:30）

### 19.1 之前所有"读不回输出"的失败是同一个误判

我曾判断是 Python 绑定 3.39 与库 3.33.1 ABI 不一致。**错**。

真实原因：板上当时烧的是**独立检测器位流**（`ip2_bd_wrapper.bin`），里面没有 AI_Mate，
ZG330 后端初始化失败（`Session::bindToBackendsByOrder` → `ZG330BackendNode::init`），
报错被吞成一句 `MMU isn't enabled, Please enable MMU first!`，
之后所有 Tensor 读写自然全部 `InternalError`。

换三域位流（`ours3d_s2.bin`）后 `Session.Create` 一次通过，`read` 立刻可用。

### 19.2 正确的读法（三行）

```python
outs = sess.forward([tensor])          # 前向
buf = bytearray(8)                     # 2 个 float32
outs[0].read(buf, 0, 8)                # 读回
probs = np.frombuffer(bytes(buf), dtype=np.float32)
```

`waitForReady()` 在 Python 绑定里签名不匹配（要求别的参数），但不调也能读。
官方的 `Tensor.dump(f, fmt)` 这条路在 Python 里仍报 InternalError（fmt 语义未知），不用它。

| 文件 | 位置 | 内容 |

| `deps/modelzoo_utils/include/ai_example/yolov5_npu_actor.hpp` | L331~336 | `forward()` 后必须对每个 tensor 调 `waitForReady()` |
| `deps/modelzoo_utils/include/icraft_utils.hpp` | L883 | `output_tensors[i].dump(os, fmt)` |
| `deps/modelzoo_utils/include/icraft_utils.hpp` | L901~913 | `zg_backend->forward_info->memchunk_map` → `mem_chunk->read()` |

### 19.4 级联实测（板上，三域位流）

`ps/cascade.py`：PL 候选 → 按面积定裁剪边长 → 缩到 128×128 → cls128 → 阈值过滤。
