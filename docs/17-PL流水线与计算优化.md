# 17 · PL 流水线设计与计算优化

> 本文重点说明检测链路的流水线结构、存储组织与计算优化。FPGA 赛道中硬件设计本身是评分点，因此这里把资源与吞吐的取舍写完整。
> 所有数字都标了来源：**【实测】**＝Procise 综合/仿真得到，**【推算】**＝按公式算的。
> 单位约定：`W×H = 640×360 = 230,400` 像素；工作时钟 **100 MHz**（板载 200 MHz 差分晶振 ÷2）。

## 2. 三级流水线总览

```
            ┌──────────────┐   ┌──────────────┐   ┌──────────────┐
 像素流 →   │ ① Top-Hat 5×5│ → │ ② CFAR 31×31 │ → │ ③ CCL 连通域 │ → 36 B 候选表
 (8bit)     │  行缓存/开运算│   │  双滑动盒+判决│   │ 单趟标记/并查集│
            └──────────────┘   └──────────────┘   └──────────────┘
             延迟 ~4 行延迟 ~30 行帧尾 6 个状态
```

| 级 | 文件 | 每拍处理 | 流水延迟 | 片上存储（bit，640×360） | 实测 LUT |
|---|---|---|---|---|---|
| ① Top-Hat | `win5.v` ×2 + `tophat_5x5_stream.v` | 1 像素 | `2W+3` ≈ 2 行（×2 级）+ 原图延迟 `4W+7` | 41,024 + ~20,552 ≈ **61.6 K** | 833 |
| ② CFAR | `cfar_threshold_stream.v` | 1 像素 | `2×CENTER_OFF` ≈ 30 行 | **≈ 265 K** | 6,506 |
| ③ CCL | `candidate_extract_stream.v` | 1 像素（标记阶段） | 帧尾 S_MERGE/S_POST/S_SORT/S_OUT | 8,960 | 37,270 |
| 合计 | — | — | — | **≈ 335 Kbit**（= 5.2 K LUT 当量） | 44,610（站点数）|

接口统一为 AXI-Stream 风格五线：`i_data[7:0] / i_valid / i_ready / o_data / o_valid (+o_ready)`，反压逐级传递。

## 3. ① Top-Hat：把「开运算」拆成两次 5×5 形态学

**算法**：`TopHat(I) = I − opening(I) = I − dilate(erode(I, 5×5), 5×5)`
开运算会抹掉「比结构元小的亮块」，相减后只剩小亮块（低慢小目标）。

关键设计 1：行缓存用循环 RAM，不用移位寄存器
5×5 窗口需要同时看到 5 行。教科书写法是移位寄存器链：
`4 行 × 641 × 8 bit = 20,512 个触发器 / 每个 win5 实例`，两个实例 = 41,024 个触发器（占全芯片 157,200 的 26 %，纯浪费）。
本项目改为深度 W+1 的循环 RAM：写指针 `wp` 自增，读地址 `rp = (wp+1) mod (W+1)` 恰好取出 W 拍前的像素；`fill < W` 期间输出 `PAD` 值（腐蚀用 255、膨胀用 0），与原来「复位全 PAD」的行为逐位等价。
→ 41,024 个触发器 → 41,024 bit LUTRAM（≈ 640 LUT 当量），行为不变（有共仿真为证）。

关键设计 2：因果窗口的对齐
流水线拿不到「未来」的行，所以 `win5` 输出的是以 `(r−2, c−2)` 为中心的窗口（因果窗口）。开运算经过两级后有效中心变成 `(r−4, c−4)`，因此原图必须延迟 `TD = 4W+7` 拍再相减（同样用循环延迟线，深度 `TD+2`，延迟 `TD`）。
副作用：图像**底部 4 行**没有足够行输入（死区），左右边界各 2~3 像素回绕。这是因果窗口的固有代价，已在文档与 README 中标注；对检测的影响见 §7。

为什么用「先腐蚀再膨胀」而不是一次 5×5 排序：两次 5×5 只需 `2×(min/max 各 24 次比较 + 5 次归约)`，无乘法器，组合深度浅，容易收敛时序。

## 4. ② CFAR：两趟全帧 → 单趟双滑动盒

### 4.1 算法与「为什么流式很难」
CFAR 判决：`x > μ + K·σ + FLOOR`，其中 `μ`、`σ` 是 31×31 窗口内的均值与标准差，`K=4`、`FLOOR=3`（与 PS 侧 `detect_v1.py` 完全一致）。

- **全帧版**（`cfar_threshold.v`，保留作参考）：用 **2D 积分图** `integral[0:H-1][0:W-1]`，4 次查表 + 3 次加减得到任意窗口和 → 两趟：先整帧算均值存 `mean_bram`，再整帧算 `|x−μ|` 的平方。
  代价：`img_bram + mean_bram` 各 230,400×8 bit = **3.7 Mbit**，且索引含除法（`cnt/W`、`cnt%W`），综合器无法推断 RAM → 爆炸。
- **流式版**（`cfar_threshold_stream.v`，主线）：列和增量 + 31 项 FIFO。
  `col_sum[c] += x(r,c) − x(r−31,c)`，再把 31 个列和相加 → 窗口和，**O(1)/像素**，不需要整帧存储，只需要 31 行的环形延迟线。

### 4.2 双盒因果对齐（本项目最硬的一处推导）
流式下有两个串联的滑动盒：盒 1 算 `μ`，盒 2 算 `E[(x−μ)²]`。
盒 1 在虚拟位置 `t` 的输出中心是 `t − CENTER_OFF`（`CENTER_OFF = 15 行 + 15 列`），而盒 2 的输入流本身又被延迟了 `CENTER_OFF`，所以：

```
diff(t) = |x(t − CENTER_OFF) − mean(t)|        ← 必须是同一像素
盒2 输出中心 = t − 2·CENTER_OFF                 ← 比盒1 再低 15 行/15 列
```

因此两个盒必须用两套边界裁剪除数（这是最初 949 处误差的根因）：
- `area1 = clip(row−15)·clip(col−15)` → 给 `μ`
- `area2 = clip(row−30)·clip(col−30)` → 给 `σ²`

裁剪函数与 PS 侧 OpenCV `boxFilter` 的 `max/min` 一致：
`clip(u) = (u<15) ? u+16 : ((u ≥ H−15) ? H+15−u : 31)`。

另外：`diff` 只能在**真实图像像素**上计算（`p_in` 门控），否则 PAD 位置的 `x=0` 配上合法的角落均值会造出巨大虚假偏差，污染 MAD 统计——这是从 949 差异降到 0 的第二个修复。

### 4.3 计算优化 1：不开方判决
原始比较 `x > μ + K·σ + FLOOR`，其中 `σ = sqrt(E[x²] − μ²)`。开方在硬件上贵且慢。设窗口面积 `A`，`S1 = Σx`，`S2 = Σx²`：

```
μ = S1/A ,  σ = sqrt(A·S2 − S1²) / A
x > μ + K·σ + FLOOR
  ⇔  A·x − S1 − FLOOR·A  >  K·sqrt(A·S2 − S1²)
  ⇔  L > 0  且  L² > K²·(A·S2 − S1²)          （L ≜ A·x − S1 − FLOOR·A）
```

整式两边平方，开方彻底消失，只剩整数加减乘和一次比较。位宽核算：
`L ≤ 245,055`（18 bit）、`L² ≤ 6.01e10`（36 bit）、`A·S2 − S1² ≤ 6.01e10`（36 bit）、`K²·(·) ≤ 9.6e11`（40 bit）。
该等价性已用 Python 双模型验证：整数判决与浮点判决在 4,096 + 9,216 个像素上**完全一致**。

### 4.4 计算优化 2：判决路径 4 级流水
最初把「31 项加法树 → 20 位乘法 → 减法 → 再一级 20 位乘法 → 比较」全压在一个 10 ns 周期里，**物理上不可能收敛**（单是两级 20 位乘法串联就超过 10 ns）。现拆成 4 级，级间插寄存器：

| 级 | 这一级做什么 | 组合逻辑规模 |
|---|---|---|
| L0 | 31 项加法树 → `ws1`（Σx）、`ws2`（Σx²） | 5 级 LUT 加法树 |
| L1 | `ws1²`、`A·ws2`、`x·A`、`FLOOR·A` | **每项只有一次乘法** |
| L2 | `A·S2−S1²`、`K²·var`（常数乘法→移位）、`L` 与 `|L|` | 只有减法 |
| L3 | `detect = (L>0) && (L² > K²·var)` | 一次乘法 + 比较 |

`x_mid`（`o_enh`）与 `out_gate`（`o_valid`）同步延迟 4 拍对齐；流水线每拍都推进，帧尾自动排空（不在 `adv` 时整组清零，避免重复采样）。
**改完仿真逐位一致**：cfar64 = 0 差异、cfar128 = 0 差异、全链 = 0 差异。

### 4.5 存储账本
| 缓冲 | 深度 × 位宽 | 用途 | bit |
|---|---|---|---|
| `rb1` | 20,306 × 8 | 31 行竖直延迟（两个盒的移出值） | 162,448 |
| `rb2` | 9,841 × 8 | 中心像素 `x(t−CENTER_OFF)` | 78,728 |
| `cs1` / `cs2` | 655 × 14 / 655 × 22 | 列和（灰阶 / 平方） | 23,580 |
| `f1` / `f2` | 31 × 14 / 31 × 22 | 31 项水平 FIFO | 1,116 |
| 合计 | — | — | **≈ 265 Kbit** |

对照全帧版 3.7 Mbit：**存储降到 1/14**，而且全部是 1 写 1 读（`rb1` 为 1 写 1 读，`rb2` 同），可以干净地推断成 LUTRAM。

## 5. ③ CCL：全帧三张图 → 两行标签 + 单趟即时累加

### 5.1 旧结构的问题
旧版先把整帧存三张图：`bin_bram`（N×1）、`enh_bram`（N×8）、`label_bram`（N×7）≈ **3.7 Mbit**，然后：`S_LOAD → S_LABEL → S_UNION → S_ACCUM → S_SORT → S_OUT` 六趟扫全帧。

### 5.2 新结构：单趟标记 + 并查集 + 即时累加
- **只保留两行标签**：`lbl_even[0:W-1]`、`lbl_odd[0:W-1]`（各 640×7 bit），按行号奇偶交替，永远只存「上一行」和「当前行」。
- **因果四邻居**：左 `nb_l`、左上 `prev_ul`、上 `prev_t`、右上 `prev_ur`（8 连通在光栅扫描下只需这四个）。
- **并查集**：`min_nb = min(4 邻居)`，`new_lbl = (min_nb≠0) ? min_nb : 下一个新标签`，同时把四个邻居的 `parent[]` 指向 `min_nb`（编号恒向小合并，天然无环）。
- **即时累加**：标记的同一拍就更新该标签的 `carea / csumx / csumy / cpeak`（面积、x 累加、y 累加、峰值）——**不用第二趟扫图**。
- 帧尾依次：`S_MERGE`（子标签并入根）→ `S_POST`（算质心 + 面积过滤）→ `S_SORT`（选择排序取 top-5）→ `S_OUT`（36 字节）。

### 5.3 计算优化：128 个除法器 → 2 个
`S_POST` 原来写成 `for (i = 0; i < MAX_COMP; i = i + 1)` 在**一个时钟内**展开（`MAX_COMP = 64`）：
`cx[i] <= (csumx[i] + carea[i]/2) / carea[i]`，`cy` 亦然 → 128 个 16 位变量除法器，实测 11,179 个 `LCARRY4`（≈ 4.4 万加法器位）、CCL 单模块 104,950 LUT。
改成每个时钟处理一个标签（引入游标 `pi`）后只剩 2 个除法器：CCL 掉到 37,270 LUT，`LCARRY4` 从 11,179 降到 **217**（−98 %）。

### 5.4 为什么块 RAM 用量是 0（设计选择，不是缺陷）
我们的存储访问模式是 1 写 3 读 / 1 写 2 读（同拍读三个不同地址），而块 RAM 最多 2 个端口，物理上映射不了。所以全部推断成 **LUTRAM**（每个 LUT 实现 128×1 双口存储 = 每 64 bit 折 1 个 LUT）。
- 好处：块 RAM 253 块全空（留给未来做帧缓存/多路并行），LUTRAM 读延迟低、同拍多读天然支持。
- 代价：335 Kbit 存储 ≈ 5.2 K LUT 当量（占总量 8 %）。
- 而且：230,400 深度超过块 RAM 单块最大深度 32,768，即使全是单口也要拆 bank，全帧方案估算需要 269 块 > 器件 253 块 → 全帧思路在本器件上根本不成立，这也是必须做流式的硬件原因。

## 6. 时序：约束与待验收指标

| 时钟 | 来源 | 约束 | 频率 |
|---|---|---|---|
| `sys_clk`（200 MHz） | 板载差分晶振 C8(P)/C7(N)，`DIFF_SSTL15` | `create_clock -period 5.000` | 200 MHz |
| 工作时钟（100 MHz） | RTL 内 2 分频 → `BUFG` | `create_generated_clock -divide_by 2` | 100 MHz |
| AXI 时钟 | 同工作时钟 | 随 PS HP 口，最高 100 MHz | 100 MHz |

要写进文章的时序指标（等综合/布局布线报告）：
- `WNS`（最坏负 slack）≥ 0 才算时序收敛；负值说明要插流水或降频
- `TNS`（总负 slack）、失败端点数量
- 最坏路径的起止点（哪个模块、哪一级）
- 建立/保持时间余量

已知风险（诚实记录）：上一版位流的时序报告只分析了 **1 个端点**（因为约束里只有 200 MHz 输入时钟，没有 100 MHz 工作时钟），等于**没做时序验收**。加上真实 100 MHz 生成时钟后，全设计 STA 在本工具上会爆内存（16 GB / 28 分钟无输出），因此改用**小规模探针** `synth/probe_cfar.tcl`（只综合 CFAR，约 6.5 K LUT）单独量 100 MHz 域的 slack。
判决路径已按 §4.4 流水化，预期可收敛，但**以探针报告为准**。

## 7. 验证方法

1. **单元回归** `pl/tools/run_sim.py`：每个模块 + 全链，与 Python 参考模型逐像素/逐字节比对。
   基线：tophat 186（OpenCV `BORDER_REFLECT_101` 边界语义差异，旧版同样 185，非本次引入）、cfar64 **0**、cfar128 **0**、ccl **0**、chain **0**。
2. **新旧共仿真** `synth/equiv/tb_chain_equiv.v`：重构前的 HEAD 版（`g_*`）与流式版并排跑同一激励，128×72 全链输出 VERDICT IDENTICAL（`bin_mis=0`、`enh_mis=0`、`ccl_bytes mis=0`、`hold_err=0 drop_err=0`）。
3. **握手安全性**：两个相同模块实例，一个接恒 `o_ready`、一个接随机反压，输出必须一致（`tb_stall_self.v` → `VERDICT STALL-SAFE`）。这项测试曾抓出 `win5`/`tophat` 输出寄存器未按 `o_ready` 使能的真实 bug。
4. **AXI 全链** `tb_axi_top.v`：模型 1.31 MB DDR 存储，AXI 读帧 → 流水线 → 候选表写回，`VERDICT AXI-TOP-OK`（36 字节 0 差异、`STATUS=0x00010302`）。
5. **板级自测** `tb_board_pattern.v`：128×72 图案（含大块，用于验证面积上限过滤），3 帧 × 每帧 4 候选，坐标/面积/峰值正确。

## 8. 后续（还差什么）

1. **时序验收**：跑 `synth/probe_cfar.tcl` 拿 CFAR 在 100 MHz 下的 slack。
2. **可上板位流**：`synth/board_ip2.tcl`（自测版，内部图案 → LED 显示候选数）。
3. **PS 对接**：`ip2_board_axi_top.v` 已就绪，需要在 Procise/Vivado 里建 block design（PS7 + AXI Interconnect + 本模块），寄存器/状态字语义已与 `ps/pl_link.py`、`docs/14` 对齐。
4. **摄像头**：MIPI CSI（J16）需 PS 侧驱动 + PL 侧 ISP（Bayer→RGB），建议先用 USB 摄像头或离线帧验证全链。
5. **并行度提升（可选）**：当前 61.9 % 资源，理论上可再复制一路做 2 路并行把吞吐翻倍，但 123 % 装不下；可行的是把 CFAR 的双盒复用或把 CCL 的 `lbl_even/lbl_odd` 改成 LUTRAM（省约 26 K LUT），腾出空间。
