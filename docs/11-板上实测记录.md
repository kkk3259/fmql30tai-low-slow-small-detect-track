| 包大小 | 4,206,098,112 字节 |

| 烧写工具 | imageUSB（PassMark），Write image to USB drive + Post Image Verification |
| 目标卡 | 64GB SDXC，61,911,682,560 字节（57.66 GiB）|

### 1.2 踩过的坑：卡容量不足

首次误用 32GB 卡（实测 31,075,107,840 字节 = 28.94 GiB）烧写，imageUSB 日志：

```
Warning: Destination Drive (31077695488 bytes) is smaller than the image file (31914983424 bytes).
Continuing on Drive ... No drive verification will be performed
Wrote past the end of the drive
```

**结论：镜像需要 ≥ 29.72 GiB 的卡，32GB 卡（标称）实际只有 28.94 GiB，差 837 MB 装不下。**
**⇒ 必须用 64GB 卡。** 该 32GB 卡分区表已被写坏，需 `diskpart clean` 后才能复用。

### 1.3 启动配置（手册 4.2）

板上有 4 组 3 针跳线帽（`J1`~`J4`），对应 `MIO2`/`MIO3`/`MIO4`/`MIO5`。
每组 3 针从上到下为 `VCC3V3` / 信号 / `GND`，跳线帽骑「上+中」= 1，「中+下」= 0。

| 跳线 | 信号 | SD 卡启动设定 |
|---|---|---|
| **J4** | MIO5 | **1**（上+中）|
| **J3** | MIO4 | **1**（上+中）|
| **J2** | MIO3 | **0**（中+下）|
| **J1** | MIO2 | **0**（中+下，级联模式）|

启动模式表（手册 4.2）：

| BOOT MODE | MIO5 | MIO4 | MIO3 |
|---|---|---|---|
| JTAG | 0 | 0 | 0 |
| QSPI | 1 | 0 | 0 |
| **SD CARD** | **1** | **1** | **0** |

`MIO6` = 0 → PLL Enabled；`MIO7`/`MIO8` = 1/1 → 1.8V（SD 卡要求 BANK501 = 1.8V）。
**这三个不是跳线帽，是固定电阻上下拉，出厂已配好，不需要动。**

## 三、NPU 现状（关键结论）

### 3.1 运行时库已预装

`/lib/aarch64-linux-gnu/` 下有 13 个 Icraft / ZG330 相关库：

```
libicraft_xrt.so                      Icraft Runtime 核心
libicraft_zg330backend.so             ZG330 后端
libicraft_xir.so                      XIR 中间表示
libicraft_xir_serialize_flatbuffers.so
libicraft_utils.so
libicraft_hostbackend.so              host（CPU）后端
libicraft_pl_sim.so                   PL 仿真后端
libicraft_buyibackend.so
libicraft_buyi_sim.so
libaxizg330aiu.so                     AXI 访问 AI Unit
libsocketzg330aiu.so                  socket 封装
libcustomop.DetPostZG.so              检测后处理算子
libmockzg330.so                       mock 测试后端
```

### 3.2 但缺少运行入口

```
$ ls /dev | grep -iE "npu|icraft|zg"
（无）

$ ls /sys/class | grep -iE "npu|ai|icraft|zg"
（无）

$ lsmod | grep -iE "npu|icraft|zg"
（无）
```

`ps_app.py` 的 `detect_backend()` 能成功 `import icraft`，但因无可用 NPU 设备，回退到 `placeholder`：

```
[判别] 后端 = npu（30TAI / Icraft）
[判别] 该平台无 NPU，回退占位：30TAI 上接入 Icraft；当前平台无 NPU
```

**⇒ 结论：NPU 的「用户态运行时」齐全，缺的是「板端推理入口程序（runtimeapp）」和「驱动/设备节点」。**

`libaxizg330aiu.so` 的存在提示：ZG330 很可能通过 **AXI + U-DMA-BUF** 访问（而非字符设备），因此需要先加载 PL bitstream。

## 五、性能瓶颈分析

### 5.1 耗时构成（真实 630 帧）

```
算法本体 = 57.87（检测）+ 0.56（裁ROI+判别）+ 1.51（跟踪）= 59.94 ms  →  约 16.7 fps
视频编码 = 88.89 ms（占 60%）
端到端   = 148.83 ms                                                  →  5.92 fps
```

### 5.2 两个瓶颈与对应加速手段

| 环节 | 板上耗时 | 加速手段 | 负责人 | 目标 |
|---|---|---|---|---|
| **② 检测 detect** | **57.87 ms** | **PL 的 IP1（预处理）+ IP2（检测）** | **P** | 1~2 ms |
| **⑥ 渲染 render** | **88.89 ms** | **VPU（`amvx`）硬编码** | **S** | 5~10 ms |

### 5.3 PC vs 板子对比

| 环节 | PC | 板子 | 倍数 |
|---|---|---|---|
| 检测 detect | 1.87~4.5 ms | 57.87 ms | 约 13~31× |

**⇒ 检测是 PL 加速收益最大的环节。**

### 5.4 候选数观察

- **合成序列 1.17/帧** —— 场景干净
- **真实视频 4.91/帧** —— **`topk=5` 顶格饱和**

**⇒ 真实场景虚警远多于合成，需要 NPU/PL 判别过滤。这也说明 PL 加速后可以「提高 topk 或收紧阈值」而不牺牲速度。**
