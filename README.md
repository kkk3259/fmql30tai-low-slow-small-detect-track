### 真实数据的关键发现

同一套算法在**合成序列**与**真实视频**上的表现差异，以及由此得出的设计结论：

| 指标 | 合成序列 | 真实视频 | 说明 |
|---|---|---|---|
| 检测层 Pd | 94.7 % | **40.8 %** | 差距源于**信噪比**，非参数问题 |
| 跟踪层成功率 | 98.7 % | **97.0 %** | ⭐ **几乎不受影响** |
| 虚警 | 384 次/分 | 12797 次/分 | 真实杂波强 |

- **机理（实测，非推测）**：目标处 Top-Hat 增强值 **34.87**、CFAR 门限 **25.07**（`k×σ≈22` + `floor=3`）→ 比值 **1.39**，**单帧信噪比不足**。
- **已排除的路径**（实验否定）：扩大候选数（`--topk 16`，Pd 40.8→41.0 %）、改大形态学结构元（`--tophat 15`，Pd 40.8→**29.2 %**）。
- **有效的手段**：**时域增强**（运动补偿 n=16）→ 虚警 **22360 → 1137 次/分**（−95 %）、候选 **7.52 → 1.87 个/帧**（−75 %）、跟踪成功率 **97.0 → 97.1 %**，且**候选数下降直接使 NPU 推理负载减轻约 4 倍**。

本仓库**不假设任何人的本机路径**。文档与命令里出现的路径都是**示例**，请按自己的环境替换：

| 示例路径 | 是什么 | 可否自定 |

> 如果 `python` 命令报错（它指向微软商店的占位程序），就用自己环境的完整路径调用，例如 `D:\你的路径\venv\Scripts\python.exe`。

## 快速开始（30 分钟跑通）

```powershell
# 1) 取代码（Gitee 是主力仓库）
git clone https://gitee.com/kkk3259/fmql30tai-low-slow-small-detect-track.git
cd fmql30tai-low-slow-small-detect-track

# 2) 跑软件基线（会自动生成合成测试视频）
D:\lowslow\venv\Scripts\python.exe baseline\run.py --src synth          # v0 增强
D:\lowslow\venv\Scripts\python.exe baseline\detect_v1.py --src synth     # v1 检测
D:\lowslow\venv\Scripts\python.exe baseline\track_v2.py --src synth      # v2 跟踪
D:\lowslow\venv\Scripts\python.exe baseline\detect_v3.py --src synth --mode mc   # v3 时域增强

# 3) 跑完整集成流水线
D:\lowslow\venv\Scripts\python.exe ps\ps_app.py --src synth

# 4) 用真实视频（自动加载同名 _gt.csv 真值）
D:\lowslow\venv\Scripts\python.exe ps\ps_app.py --src 你的视频.mp4 `
    --temporal mc --n-acc 16 --vel-x 0.044 --vel-y -0.002
```

**成功的标志**：`run.py` 打出 `+21.66 dB`；`track_v2.py` 打出 `跟踪成功率 98.7 %`；`ps_app.py` 打出各环节耗时并生成 `results/app_demo.mp4`。

> ⚠️ 必须用 `D:\lowslow\venv\Scripts\python.exe`，**不要用 `python`**（它指向微软商店的占位程序，会报错）。

## 硬约束提醒（摘自官方文件，写代码前先看）

- lite 版**未焊接**：PL 端千兆网、PL eMMC、CAN、RTC、SMA、SFP1、SDI 输入 3/4、SDI 输出、EEPROM、可调 GT 时钟、电流监控 → 视频输入只能走 **PS 侧**（USB 摄像头 / TF 卡序列 / 网口推流）
- **无 RTC**：断电后系统时间丢失，演示前必须对时
- HDMI **固定 720P60**（1080P60 部分显示器闪屏）
- USB2.0 带宽有限：720P YUYV 需 55 MB/s **超限** → 相机必须用 **MJPG**
- PS 主时钟必须 50MHz（不可用 33.333MHz）
